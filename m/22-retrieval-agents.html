Retrieval, Tools, and Agents

Most RAG failures are retrieval failures misdiagnosed as generation failures.

on this page

Why this module exists

A language model knows what was in its training data and nothing else. Everything you actually need it to know — your documents, this week's numbers, the result of the query it just wrote — arrives through the context window, which is finite, expensive, and badly attended to. Retrieval, tool use, and agents are all answers to the same problem: getting the right few thousand tokens in front of the model at the right moment, then acting on what comes back. The field is unusually susceptible to framework worship, because a demo with two documents looks like magic and a production system with two hundred thousand documents fails in ways the demo cannot reveal. This module is about the arithmetic that separates those cases: recall@$k$, the quadratic cost of long context, the compounding of per-step reliability, and the diagnostic that tells you whether to blame the retriever or the generator.

Prerequisites check

  1. What is the KV-cache cost per token, and how does attention compute scale with context length $T$?
  2. What is cosine similarity, and why are embeddings usually L2-normalised?
  3. What does a softmax over the vocabulary compute, and what is a temperature?
  4. With cross-entropy over a softmax, what is the gradient with respect to a logit?
  5. In a chat model, what is the difference between a system message, a user turn, and tool output?
Answers 1. KV cache is $2Ln_{kv}d_hb$ bytes per token, linear in $T$; attention compute per layer is $O(T^2 d)$. 2. $\langle \mathbf{a},\mathbf{b}\rangle/(\|\mathbf{a}\|\|\mathbf{b}\|)$; normalising makes the inner product equal the cosine, so nearest-neighbour search is a dot product. 3. $\operatorname{softmax}(\mathbf{z}/\tau)$; temperature rescales logits before normalising, controlling sharpness. 4. $\partial \mathcal{L}/\partial z_i = p_i - y_i$. 5. A system message is provider-authored instruction, a user turn is the request, and tool output is data returned by a function call — which the model reads as text, which is exactly the injection problem. **M15** covers 1 and 3; **M12** covers why attention is quadratic.

Learning objectives

  • Compute the token and attention cost of stuffing a document set into context, and say when retrieval beats stuffing.
  • Derive the InfoNCE loss and its gradient, and explain what hard negatives and temperature do to it.
  • Implement BM25, explain each of its three factors, and fuse it with a second ranking using reciprocal rank fusion.
  • Estimate HNSW and IVF-PQ recall/latency trade-offs from their parameters.
  • Diagnose a RAG failure as retrieval, synthesis, or over-retrieval using a measurement rather than an opinion.
  • Write a tool schema and describe the failure modes of argument grounding and tool selection.
  • Compute the end-to-end reliability of an $n$-step agent loop and the token cost of a multi-agent hop.

Core concepts

The context window is a scarce resource

Intuition. A context window is a desk, not a warehouse. Everything on it is in the way of everything else, and you pay rent per square centimetre per second.

Formal definition. Attention cost per layer is $O(T^2 d)$ compute and the KV cache is $O(T)$ memory per layer, so a request carrying $T$ tokens costs $O(T^2)$ to process once and then holds $2Ln_{kv}d_hb\,T$ bytes for the life of the generation. At $T = 100{,}000$ with $L=32$, $n_{kv}=8$, $d_h=128$, bf16, that is $100000 \times 128\ \text{KiB} = 12.8$ GB of cache for a single request.

Why it is built this way. The quadratic term is why "just put everything in the context" fails economically before it fails technically: doubling the context quadruples prefill compute and doubles the cache. Retrieval exists because the information density of a stuffed context is terrible — a 100k-token context where 2k tokens matter is 98% distraction, and models measurably attend worse to material in the middle of a long context than at either end.

Worked micro-example. Stuffing 200 documents of 800 tokens costs 160k tokens; retrieving the top 5 costs 4k tokens plus a 30 ms vector search. At 15k prefill tokens/s, 160k tokens is 10.7 s before the first output token, against a target TTFT of 500 ms.

Embeddings and contrastive training

Intuition. Put things that answer the same question near each other in space, without ever telling the model what the question means.

Formal definition. A bi-encoder maps query and document independently, $\mathbf{e}_q = f(q)$, $\mathbf{e}_d = g(d)$, and scores them with $s(q,d) = \langle \mathbf{e}_q, \mathbf{e}_d\rangle/\tau$. Training uses in-batch negatives with InfoNCE over a batch $\mathcal{B}$:

$$ \mathcal{L} = -\frac{1}{|\mathcal{B}|}\sum_{i \in \mathcal{B}} \log \frac{\exp(s(q_i, d_i^{+}))}{\sum_{j \in \mathcal{B}} \exp(s(q_i, d_j))} . $$

Why it is built this way. The independence of the two encoders is what makes retrieval fast: documents are embedded once, offline, and queries at request time, so scoring is a matrix multiply rather than a forward pass per candidate. The price is that query and document never see each other, so fine-grained interactions are invisible — exactly what a cross-encoder later restores, at one forward pass per candidate.

Worked micro-example. A batch of 256 pairs gives each query 255 negatives for free. With $\tau = 0.05$, a positive at cosine 0.9 gives a logit of 18 and a negative at 0.3 gives 6 — a ratio of $e^{12}$, so the positive dominates and the gradient nearly vanishes. That is the easy-negative problem, and it is why hard-negative mining and larger batches both help.

Retrieval: lexical, dense, hybrid, and reranked

Intuition. Keyword search knows when a term is rare; vector search knows when two sentences mean the same thing without sharing a word. Neither is a superset of the other.

Formal definition. BM25 multiplies three factors per query term:

$$ \text{score}(q,d) = \sum_{t \in q} \operatorname{idf}(t) \cdot \frac{f_{t,d}\,(k_1+1)}{f_{t,d} + k_1(1 - b + b\,\frac{|d|}{\mathrm{avgdl}})} . $$

The $\operatorname{idf}$ term rewards rarity; the fraction saturates toward $k_1 + 1$ as $f_{t,d}$ grows, so a term appearing fifty times is not fifty times more relevant; and $b$ interpolates between no length normalisation ($b=0$) and full normalisation by relative length ($b=1$). HNSW builds a hierarchy of proximity graphs and descends greedily from a sparse top layer, with M controlling graph degree and ef the breadth of the search — larger ef is monotonically more recall and more latency. IVF-PQ clusters vectors into nlist cells, probes only nprobe, and compresses each vector into $m$ subspace codes: a 768-dimensional float32 vector is 3072 bytes, and at $m=96$ 8-bit codes it is 96 bytes, a 32-fold reduction that costs recall.

Why it is built this way. Lexical and dense retrieval fail in different places, which is the entire argument for hybrid search: BM25 fails on paraphrase (no shared terms), dense retrieval fails on rare identifiers, exact codes, and numbers (the embedding compresses them away). Reranking then spends a cross-encoder on the top 50 to 100 candidates, where full attention over (query, passage) is affordable and far more accurate.

Worked micro-example. In the implementation later, a query with no lexical overlap puts BM25's gold document at rank 6 of 6 — a total miss. Reciprocal rank fusion with a second ranking pulls it to rank 3, restoring recall@3 from 0 to 1 without beating the strong list on MRR. Fusion buys robustness, not accuracy; weighting the better retriever higher improves MRR from 0.33 to 0.50.

Chunking, and the ways RAG fails

Intuition. A chunk is the unit of retrieval, so a badly cut chunk makes the right document unfindable even though it is sitting in the index.

Formal definition. A chunking strategy is a partition of each document into spans plus metadata. Mean-pooled embedding dilution is the governing arithmetic: if a 500-token chunk contains 20 tokens that answer the query, the answer contributes about 4 percent of the pooled vector and cosine similarity is dominated by the other 96 percent.

Why it is built this way. Splitting is unavoidable because embeddings degrade on long spans and context is expensive, but every split can cut a table from its header, a pronoun from its antecedent, or a definition from its use. The standard fixes are structural: split on document structure rather than character count, carry parent-section metadata so a retrieved chunk can be expanded, overlap by a sentence, and store the heading path with every chunk so the embedder sees what the passage is about.

Worked micro-example. The four failure modes, with the diagnostic that separates them:

Failure Symptom Measurement
Wrong retrieval gold passage never in the top $k$ recall@$k$ against gold passages
Right retrieval, wrong synthesis gold in context, answer still wrong conditional accuracy given gold retrieved
Over-retrieval many chunks, answer drifts or ignores them accuracy vs $k$, usually peaking around 3–10
Not in the corpus model answers anyway abstention rate on unanswerable queries

The single most useful diagnostic is the oracle test: insert the gold passage by hand and re-run. If accuracy jumps, you have a retrieval problem and no prompt engineering will fix it. Teams that skip this step spend weeks tuning a generator whose input never contained the answer.

Tools and the agent loop

Intuition. A tool call turns a language model from a text generator into something that can act — and every action is a new way to be wrong.

Formal definition. A tool is a name, a description, and a JSON schema for arguments; the model emits a call as structured text, the harness validates it, executes it, and returns the result as a new message. The agent loop is: observe the task, choose an action (tool call or final answer), execute, append the observation, repeat until a termination condition. ReAct interleaves reasoning with actions; plan-and-execute separates a planning pass from execution; reflection adds a critique step feeding the next attempt.

Why it is built this way. The loop exists because a single forward pass cannot observe the world. Its cost is that errors become state: a wrong argument produces a wrong observation, which conditions the next step, which compounds. The termination condition is the hardest part and the commonest source of runaway cost — a loop needs a step budget, a no-progress detector, and an escalation path, not just a while True.

Worked micro-example. With per-step success probability $p$ over $n$ steps, end-to-end success is $p^n$:

$p$ $n = 5$ $n = 10$ $n = 20$
0.99 0.951 0.904 0.818
0.95 0.774 0.599 0.358
0.90 0.590 0.349 0.122

A loop that is 95% reliable per step has a 36% chance of finishing twenty steps. That is why the design goal is fewer, larger, more reliable steps, and why a 20-step agent is a different engineering problem from a 5-step one.

Context engineering, memory, and multi-agent costs

Intuition. Context engineering is deciding what the model sees now, not what it might need later. Memory is deciding what to keep at all.

Formal definition. Three tiers: parametric memory in the weights (fixed at training), the working context (the current window, edited every step), and external memory (a store the model queries, which is retrieval again). Context engineering is the policies over the working tier: what to include, in what order, at what fidelity, and what to summarise or drop when the budget is exceeded.

Why it is built this way. Every token in the window competes with every other for attention and budget, so ordering is a design decision: instructions early, the question late, retrieved evidence in the middle only if you must, and truncate tool output at the tool rather than at the prompt. Summarisation and compaction keep a long-running agent inside its budget at the cost of exact detail — which is why summarised state must preserve identifiers verbatim.

Worked micro-example. A three-agent pipeline where each agent receives an 8k-token shared context and they exchange results four times costs $3 \times 8\text{k} \times 4 = 96$k input tokens, against roughly 24k for one agent doing the same work — a 4× multiplier before any quality gain, plus 4× the latency and a much harder debugging surface. Orchestration pays when subtasks are genuinely parallel or need genuinely different tools and permissions; it loses whenever the work is sequential, because the coordination tokens are pure overhead.

Agent failure modes

Intuition. Agents fail differently from models: the model can be right and the system still wrong, because the wrong thing was fed back in.

Formal definition. The recurring taxonomy: hallucinated tool calls (a tool that does not exist, or arguments violating the schema); argument grounding errors (right tool, wrong value, usually a mis-transcribed identifier); loops (repeating an action because progress is not detected); premature termination (declaring success without verification); cascading errors (one bad observation corrupting later steps); and injection through observations (attacker-controlled tool output redefining the task).

Why it is built this way. Each corresponds to a missing check, and each check is cheap relative to the failure. Schema validation and a tool allowlist stop hallucinated calls; echoing identifiers back through a deterministic path stops grounding errors; hashing observations to detect repetition stops loops; an independent verifier stops premature termination; privilege separation bounds injection.

Worked micro-example. Measure four numbers, not one: task success rate, steps to success, cost per task, and tool-call validity rate. A change that raises success from 71% to 78% while doubling mean steps from 6 to 12 and tripling cost is usually a regression in disguise, and only the four-number report makes that visible.

The algorithm, step by step

A retrieval-augmented request, end to end.

  1. Rewrite the query into a standalone search string, resolving pronouns against conversation history.
  2. Retrieve $k_{\text{first}} = 50$ candidates by BM25 and dense search in parallel, each from its own index.
  3. Fuse the two rankings with $\text{score}_i = \sum_j w_j/(60 + \text{rank}_{j,i})$.
  4. Rerank the top 50 with a cross-encoder and keep $k_{\text{final}} = 5$.
  5. Assemble the context: system instructions, then evidence with source ids, then the question last.
  6. Generate with a citation requirement, so an uncited claim is visibly unsupported.
  7. Verify that every cited source id exists in the assembled context; fail loudly if not.
  8. Log the retrieved ids, their ranks, and the answer, so a later failure can be attributed.

```text candidates = bm25(q, k=50) + dense(q, k=50) # two independent retrievers fused = rrf([rank(bm25_scores), rank(dense_scores)], weights=[1, 2]) evidence = cross_encoder_rerank(q, fused[:50])[:5] ctx = system + format(evidence) + question answer = llm(ctx, require_citations=True) assert all(c in evidence_ids for c in answer.citations) # fail loudly log(q, evidence_ids, answer, cost) ```

Complexity. Retrieval is $O(k)$ graph or list probes plus $O(50 \cdot T_{\text{chunk}} \cdot d)$ for the reranker; generation is $O(T_{\text{ctx}}^2 d)$ per layer for prefill. The economically important term is the last one, which is why $k_{\text{final}}$ is usually 3 to 10 and why reranking the whole index is never affordable.

Derivations

1. The InfoNCE gradient

Write $s_i = \langle \mathbf{e}_q, \mathbf{e}_{d_i}\rangle/\tau$ and $p_i = e^{s_i}/\sum_j e^{s_j}$, the softmax over the batch. With the positive at index $+$,

$$ \mathcal{L} = -\log p_{+} = -s_{+} + \log \sum_j e^{s_j} . $$

Differentiating with respect to a score $s_i$,

$$ \begin{aligned} \frac{\partial \mathcal{L}}{\partial s_i} &= -\delta_{i,+} + \frac{e^{s_i}}{\sum_j e^{s_j}} = p_i - \delta_{i,+}, \\[2pt] \frac{\partial \mathcal{L}}{\partial s_{+}} &= -(1 - p_{+}), \text{ and } \frac{\partial \mathcal{L}}{\partial s_j} = p_j \text{ for } j \ne +. \end{aligned} $$

Three facts follow. The pull on the positive is weighted by $(1 - p_{+})$: once the positive dominates, its gradient vanishes and further training does nothing. Every negative is pushed down with weight equal to its own probability, so the hardest negatives dominate — which is why mined hard negatives help and a batch of easy negatives trains slowly. And because the gradient depends only on $p$, the scale of the similarity is irrelevant except through the temperature, which sets the scale of $s$. The objective is also a bound: $\mathcal{L} \ge \log|\mathcal{B}| - I(q;d)$, so minimising it maximises a lower bound on the mutual information between query and document, up to $\log|\mathcal{B}|$ — the formal reason larger batches help.

2. Where BM25's saturation and length terms come from

Treat retrieval as binary classification of documents into relevant $R$ and non-relevant $\bar{R}$, and ask which class a document is more likely under:

$$ \log \frac{P(d \mid R)}{P(d \mid \bar{R})} = \sum_{t} \log \frac{P(t \text{ occurs in } d \mid R)}{P(t \text{ occurs in } d \mid \bar{R})} , $$

which sums per-term evidence — the origin of the sum over query terms. Under a two-Poisson model of term occurrence the per-term ratio grows with frequency and then flattens: a document mentioning "cache" forty times is not forty times more about caching than one mentioning it twice. The standard parameterisation of that flattening is

$$ \frac{f_{t,d}\,(k_1+1)}{f_{t,d} + k_1(1-b+b\frac{|d|}{\mathrm{avgdl}})} , $$

whose limit as $f_{t,d}$ grows is $k_1 + 1$, and whose value at $f_{t,d} = 1$ for an average-length document is $(k_1+1)/(1+k_1) = 1$. So $k_1$ controls how fast the contribution saturates — small $k_1$ saturates almost immediately, large $k_1$ approaches linear counting — and $b$ controls how much long documents are penalised, from none at $b=0$ to fully proportional at $b=1$.

3. Compounding reliability in a multi-step agent

Model each step as an independent Bernoulli success with probability $p$. The loop succeeds only if all $n$ steps succeed:

$$ P(\text{success}) = p^n, \text{ and } \mathbb{E}[\text{steps until first failure}] = \frac{1}{1-p} . $$

The second expression is why agents drift into loops: at $p = 0.95$ a failure arrives on average every 20 steps, and an agent without a progress check cannot distinguish "I have not succeeded yet" from "I am succeeding slowly". Taking logs, $\log P = n\log p \approx -n(1-p)$ for $p$ near 1, so failure probability grows roughly linearly in $n(1-p)$: to keep end-to-end success above 0.9 over 20 steps you need $p > 0.9^{1/20} = 0.9947$. That is the quantitative case for making each step more reliable or the loop shorter, and why verification steps that look redundant are worth their cost.

Implementation from scratch

BM25, reciprocal rank fusion, and the retrieval metrics, with no dependencies. The point of interest is the last block: BM25 misses a paraphrase completely, and fusion rescues it into the top three without beating the strong list.

```python import math, re from collections import Counter def tok(s): return re.findall(r"[a-z0-9]+", s.lower()) class BM25: """Lexical scoring: tf saturation through k1, length normalisation through b.""" def __init__(self, docs, k1=1.5, b=0.75): self.D = [tok(d) for d in docs] self.k1, self.b = k1, b self.avgdl = sum(len(d) for d in self.D) / len(self.D) self.df = Counter(w for d in self.D for w in set(d)) self.N = len(self.D) def idf(self, w): n = self.df.get(w, 0) return math.log(1 + (self.N - n + 0.5) / (n + 0.5)) # smoothed: always > 0 def scores(self, q): out = [] for d in self.D: tf = Counter(d) s = 0.0 for w in tok(q): f = tf.get(w, 0) if f: s += self.idf(w) * f * (self.k1 + 1) / ( f + self.k1 * (1 - self.b + self.b * len(d) / self.avgdl)) out.append(s) return out def rrf(rankings, weights=None, k=60): """Reciprocal rank fusion: score_i = sum over lists of w_j / (k + rank_i).""" weights = weights or [1.0] * len(rankings) fused = Counter() for w, ranking in zip(weights, rankings): for rank, i in enumerate(ranking, start=1): fused[i] += w / (k + rank) return [i for i, _ in fused.most_common()] def mrr(ranking, gold): return 1.0 / (1 + ranking.index(gold)) def recall_at_k(ranking, gold, k): return float(ranking.index(gold) < k) docs = [ "hybrid search fuses lexical and dense retrieval with reciprocal rank fusion", "paged attention allocates KV cache in fixed size blocks and releases them", "an agent loop calls tools and observes results until the task completes", "quantization reduces the number of bytes stored per weight", "continuous batching admits new requests into a running batch", "BM25 ranks documents by term frequency and inverse document frequency", ] q, gold = "which scoring function should I use for keyword search", 5 lexical = sorted(range(len(docs)), key=lambda i: -BM25(docs).scores(q)[i]) # In production this list comes from a bi-encoder; supplied here so the fusion # arithmetic is visible without embedding a model. semantic = [5, 0, 1, 2, 3, 4] lists = {"lexical": lexical, "semantic": semantic, "rrf(equal)": rrf([lexical, semantic]), "rrf(1:3)": rrf([lexical, semantic], weights=[1.0, 3.0])} for name, r in lists.items(): print(f"{name:11s} gold_rank={r.index(gold)+1} MRR={mrr(r, gold):.3f}" f" recall@3={recall_at_k(r, gold, 3):.0f}") ```

What to expect.

```text lexical gold_rank=6 MRR=0.167 recall@3=0 semantic gold_rank=1 MRR=1.000 recall@3=1 rrf(equal) gold_rank=3 MRR=0.333 recall@3=1 rrf(1:3) gold_rank=2 MRR=0.500 recall@3=1 ```

The query shares no terms with the gold document, so BM25 ranks it last of six: a complete miss, and a very common one. Fusion does not recover the rank-1 answer, because unweighted RRF treats both lists as equally trustworthy; it does restore recall@3 from 0 to 1, which is what matters when a reranker follows. Weighting the better retriever 3:1 improves MRR to 0.50 without changing recall. That is the honest case for hybrid search: a robustness measure against one retriever failing, not a way to beat your best retriever.

Worked example

Diagnosing a RAG system that answers 62% of questions correctly on a 300-question evaluation set.

Measurement Value Reading
End-to-end accuracy 0.62 the headline
recall@5 of the retriever 0.71 the ceiling if generation were perfect
Accuracy given gold in context 0.94 generation is not the problem
Accuracy with gold inserted by hand 0.95 confirms the 0.71 ceiling
Accuracy with $k=1$ 0.58 over-retrieval is mild
Accuracy with $k=20$ 0.60 adding distractors costs 2 points
Abstention on unanswerable items 0.12 the model answers when it should not

The arithmetic makes the decision for you. With recall@5 at 0.71 and conditional accuracy at 0.94, the attainable end-to-end score is $0.71 \times 0.94 = 0.667$, and the measured 0.62 is only 4.7 points below it. Moving generation accuracy from 0.94 to 0.97 would gain at most $0.71 \times 0.03 = 2$ points; moving recall@5 from 0.71 to 0.85 would gain $0.14 \times 0.94 = 13$ points. Any effort spent on the prompt is misallocated by a factor of six.

The abstention number is the second finding: 12% is not a capability, it is an accident, and a system that answers unanswerable questions is more dangerous than one that answers fewer questions correctly, because the failure is silent.

Common misconceptions

"RAG solves hallucination"

Retrieval changes the input distribution; it does not change the generation process. A model given five passages still produces fluent unsupported text when the passages do not contain the answer, and it does so more confidently because the context looks authoritative. What reduces hallucination is measurement — ablation on is the answer in the context — plus an abstention policy and citation verification.

"Bigger chunks are better because they carry more context"

Larger chunks dilute the embedding: a 2000-token chunk where 30 tokens matter gives the answer about 1.5% of the pooled vector. They also spend more budget per retrieval. The usual resolution is small chunks for retrieval with parent-document expansion for generation — retrieve on the precise span, hand the model its enclosing section.

"A better embedding model will fix our retrieval"

Sometimes. But recall@$k$ failures are just as often chunking artefacts (the answer split across a boundary), metadata failures (the chunk does not say what section it came from), or query failures (a pronoun with no antecedent). Swap the embedder last, after measuring which of these it is; swapping it first is the most common expensive non-fix in the field.

"Multi-agent systems are more capable than single agents"

They are more parallel and more isolated, which helps when subtasks are independent or need different permissions. For sequential reasoning they are strictly worse: each handoff re-sends context, so cost multiplies, and each hop is another place for an error to enter and be amplified. The published wins are mostly on already-decomposable tasks, and the coordination overhead is rarely reported.

"If the agent loop works on my ten test cases it will work in production"

Ten cases cannot distinguish $p = 0.95$ from $p = 0.99$, and those give end-to-end success of 0.36 and 0.82 over twenty steps. Agent reliability must be measured per step on a set large enough to estimate a rate, or you are shipping a system whose failure probability you have not measured.

Exercises

Warm-up (check understanding)

1. A 300-token chunk contains a 15-token sentence that answers the query. What fraction of a mean-pooled embedding comes from that sentence, and what does it imply for chunk size?

Solution $15/300 = 5$ percent. Similarity is dominated by the other 95 percent, so a chunk containing the answer and a chunk merely *about* the topic score similarly. Halving the chunk to 150 tokens doubles the signal share to 10 percent, which is why retrieval chunks are typically 200–500 tokens.

2. What is the KV-cache cost of a single 50k-token request with $L=32$, $n_{kv}=8$, $d_h=128$, bf16?

Solution $k = 2 \cdot 32 \cdot 8 \cdot 128 \cdot 2 = 131{,}072$ bytes $= 128$ KiB per token, so $50{,}000 \times 128\ \text{KiB} = 6.4$ GB for one request. That is why long-context serving is a memory problem and why concurrent long-context users are few.

3. In the BM25 formula, what happens to a term's contribution as its frequency grows, and why is that desirable?

Solution It saturates at $k_1 + 1$. Relevance is not linear in frequency: a document mentioning "cache" fifty times is not fifty times more about caching than one mentioning it five times. Without saturation, keyword-stuffed documents dominate the ranking.

Core (do the math)

4. Derive the InfoNCE gradient and explain what happens to the training signal when $p_{+} = 0.99$.

Solution $\mathcal{L} = -s_{+} + \log\sum_j e^{s_j}$, so $\partial\mathcal{L}/\partial s_i = p_i - \delta_{i,+}$, giving $-(1-p_{+})$ on the positive and $p_j$ on each negative. At $p_{+} = 0.99$ the positive's gradient is 0.01 and the total negative mass is 0.01 — the example contributes almost nothing. That is the easy-negative problem; fixes are larger batches, higher temperature, or mined hard negatives.

5. An agent has $p = 0.97$ per step. What is the largest $n$ keeping end-to-end success above 0.5, and above 0.8?

Solution $p^n > 0.5$ gives $n < \log 0.5/\log 0.97 = 22.8$, so $n \le 22$. For 0.8, $n < \log 0.8/\log 0.97 = 7.4$, so $n \le 7$. A 97% per-step rate sounds excellent and caps you at seven steps for an 80% target — the argument for making steps larger and fewer.

6. A 768-dimensional float32 index holds 10 million vectors. Give the raw size and the size with IVF-PQ at $m = 96$ subspaces and 8-bit codes.

Solution Raw: $10^7 \times 768 \times 4 = 30.7$ GB. PQ: $10^7 \times 96 \times 1 = 960$ MB, a 32-fold reduction. That is what makes a 10M-vector index fit on one machine, at the cost of approximate distances — which is why `nprobe` and recall must be measured, not assumed.

7. A system has recall@5 = 0.68 and conditional accuracy given correct retrieval = 0.90. What is the attainable end-to-end accuracy, and how much does fixing recall to 0.85 gain versus improving generation to 0.96?

Solution Attainable is $0.68 \times 0.90 = 0.612$. Recall to 0.85 gives $0.85 \times 0.90 = 0.765$, a gain of 15.3 points. Generation to 0.96 gives $0.68 \times 0.96 = 0.653$, a gain of 4.1 points. Retrieval is worth roughly four times as much here — the calculation teams skip.

Stretch (build or break it)

8. Extend the implementation to sweep $k$ from 1 to 20 and plot recall@$k$ and MRR. Then add hard-negative mining: for each query, add the highest-scoring non-gold document to the negative set and re-measure.

Hint Recall@$k$ is monotone in $k$ by construction, so its usefulness is in showing where the curve flattens — that plateau is your retrievable ceiling. Hard negatives change the BM25 side only if you re-weight idf; the real experiment is on the dense side, where you should see the largest MRR gain from a handful of mined negatives, because InfoNCE's gradient is dominated by the negatives with the largest $p_j$.

9. Build an agent-loop reliability harness: simulate $n$-step loops with a per-step success probability drawn from a table of failure modes, and report how end-to-end success changes when you add a verification step that catches 70% of errors at the cost of one extra step.

Hint Model the loop as a Markov chain: each step succeeds with $p$, fails silently with $q(1-r)$, and fails detectably with $qr$, where $r$ is the verification's catch rate. A detectable failure triggers a retry, which costs a step but not the episode. Verification is worth its cost precisely when $p$ is already high; at low $p$, retries dominate and the extra step just adds latency.

Self-test

  1. Give the two cost terms that make stuffing context expensive and say which dominates at long context.
  2. Write the InfoNCE loss and state why hard negatives matter in terms of its gradient.
  3. Name BM25's three factors and what each controls.
  4. What does reciprocal rank fusion compute, and what is its main assumption?
  5. State the oracle test for a RAG failure and what each outcome implies.
  6. Why does a 20-step agent with 95% per-step reliability usually fail, in one number?
  7. Give two agent failure modes, each with its cheapest mitigation.
Answers 1. Attention compute per layer $O(T^2 d)$ and KV cache $O(T)$ per layer; at long context the cache binds concurrency and the quadratic prefill binds latency. 2. $\mathcal{L} = -\log(e^{s_+}/\sum_j e^{s_j})$; the positive's gradient is $-(1-p_{+})$ and each negative's is $p_j$, so only negatives with substantial probability contribute — which is what mining arranges. 3. $\operatorname{idf}$ for rarity, the saturation fraction for frequency (plateau $k_1+1$), and $b$ for length normalisation between none and full. 4. $\sum_j w_j/(60 + \text{rank}_{j,i})$ over the lists being fused. It assumes the lists are comparably trustworthy and that low ranks carry the signal; it needs weights when one retriever is much stronger. 5. Insert the gold passage by hand. If accuracy jumps sharply, retrieval binds; if it does not, generation binds and retrieval tuning will not help. 6. $0.95^{20} = 0.358$ — a 36% chance of completing the task. 7. Hallucinated tool calls: schema validation plus a tool allowlist. Loops: hash the observation to detect repetition, plus a step budget. (Also argument grounding via deterministic id propagation, and premature termination via an independent verifier.)

Further reading

  • Karpukhin et al., "Dense Passage Retrieval for Open-Domain Question Answering" (EMNLP 2020). The bi-encoder plus in-batch-negatives recipe most retrieval stacks still follow; read the ablation on batch size and negative sampling.
  • Oord, Li, and Vinyals, "Representation Learning with Contrastive Predictive Coding" (2018). Where InfoNCE is introduced and shown to bound mutual information; this module's derivation follows their Section 2.
  • Robertson and Zaragoza, "The Probabilistic Relevance Framework: BM25 and Beyond" (2009). The definitive account of where saturation and length normalisation come from; the historical derivation explains parameters that are otherwise arbitrary.
  • Malkov and Yashunin, "Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs" (2018). Read for what M and ef control, then measure your own recall/latency curve.
  • Liu et al., "Lost in the Middle: How Language Models Use Long Contexts" (2023). The empirical basis for the claim that position within a long context matters a great deal; the effect is large and changes how you order a prompt.
  • Yao et al., "ReAct: Synergizing Reasoning and Acting in Language Models" (ICLR 2023). The canonical interleaved loop; read the failure examples, which are more instructive than the successes.
