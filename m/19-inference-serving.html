Inference Engineering and Serving

Prefill is compute-bound, decode is bandwidth-bound, and the rest is consequences.

on this page

Why this module exists

A 7-billion-parameter model that trains comfortably on one GPU can be undeliverable: it costs more per million tokens than the product can charge, returns its first token in 400 ms and then dribbles out 45 ms per token, and collapses at forty concurrent users because a structure you never had to think about during training — the KV cache — grows until it owns the device. Nearly every serving decision, from grouped-query attention to 4-bit weights to request scheduling, follows from one fact: prefill and decode are different workloads, one starved for arithmetic and one for memory bandwidth.

Prerequisites check

  1. How many tokens does one forward pass of an autoregressive decoder produce, and what must be recomputed if nothing is cached?
  2. What is the FLOP count of multiplying $\mathbf{W} \in \mathbb{R}^{d \times d}$ by $n$ input rows?
  3. What is arithmetic intensity, and what is a roofline's ridge point?
  4. With 32 query heads and 8 key/value heads, how many query heads share one key/value head?
  5. Write symmetric absmax quantization to $b$ bits in one line.
Answers 1. Exactly one; without a cache, token $t$ requires re-running the model over all $t-1$ predecessors, so $T$ tokens cost $O(T^2)$. 2. $2nd^2$ FLOPs. 3. FLOPs per byte moved from main memory; the ridge point is $\text{peak FLOP/s}$ divided by $\text{bandwidth}$, dividing bandwidth-bound from compute-bound. 4. Four. 5. $s = \max_i|w_i|/(2^{b-1}-1)$, $\hat{w}_i = s\,\operatorname{round}(w_i/s)$. Revisit **M15** if you missed 1; the roofline in **M24** is the source for 3.

Learning objectives

  • Compute a model's KV-cache footprint in bytes per token and the maximum batch it permits on a named GPU.
  • Derive the arithmetic intensity of prefill and decode, place both on a roofline, and predict which one a device bottlenecks.
  • Explain with a number why grouped-query attention raises decode throughput.
  • Implement a block-based KV allocator and continuous-batching scheduler and measure the gain over static batching.
  • Predict when 4-bit weight-only quantization does not speed anything up, and name the right lever instead.
  • Derive the expected tokens per verification step in speculative decoding and say why the distribution is unchanged.
  • Compute cost per million tokens from GPU count, hourly price, and measured throughput.

Core concepts

Prefill and decode are different workloads

Intuition. A matmul reads numbers and does arithmetic. Hand it one vector and it spends all its time fetching the weight matrix, like a cook who reads the whole cookbook to make one omelette. Hand it a thousand vectors and the cookbook is amortised.

Formal definition. A layer $\mathbf{W} \in \mathbb{R}^{d\times d}$ in bf16 applied to $n$ rows does $2nd^2$ FLOPs and moves $2d^2$ bytes, so $\mathrm{AI} = n$; likewise for a whole model. Prefill has $n = BT$; decode has $n = B$ but must also drag the cache:

$$ \mathrm{AI}_{\text{decode}} = \frac{2PB}{2P + BTk}. $$

You are compute-bound when $\mathrm{AI} > r$ and bandwidth-bound when $\mathrm{AI} < r$.

Why it is built this way. This is not a design choice; it is a dense matmul meeting a two-level memory hierarchy. Because $\mathrm{AI}_{\text{decode}}$ falls with $T$ and saturates at $2P/(Tk)$, long context pushes decode further into the bandwidth-bound regime — which is why cache compression beats weight compression at long context.

Worked micro-example. $P = 7\times10^9$ bf16 (13.0 GiB), $T = 2048$, $k = 512$ KiB, A100 80 GiB ($F = 312$ TFLOP/s, $W_{\text{HBM}} = 2039$ GB/s, $r = 153$). Prefill of 2048 tokens at $B=1$ has $\mathrm{AI} = 2048$, thirteen times above the ridge. Decode at $B=32$ moves $13.0 + 32.0 = 45.0$ GiB for 448 GFLOP, so $\mathrm{AI} = 9.9$ — sixteen times below it, predicting $45.0 \times 2^{30}/2.039\times10^{12} = 23.7$ ms against a 1.4 ms compute floor.

The KV cache: the only thing that grows with time

Intuition. It is the transcript you keep so you never re-read the book. Keep the keys and values and you pay once; drop them and you pay every step.

Formal definition. Each layer caches $\mathbf{K}^{(l)},\mathbf{V}^{(l)} \in \mathbb{R}^{T \times n_{kv} \times d_h}$, costing $k = 2Ln_{kv}d_hb$ bytes per token and $Tk$ per sequence. For $L=32$, $n_{kv}=32$, $d_h=128$, $b=2$: $k = 524{,}288 = 2^{19}$ bytes — half a mebibyte per token, 2 GiB for a 4096-token sequence.

Why it is built this way. Caching converts generating $T$ tokens from $O(T^2)$ attention work into $O(T)$ at $O(T)$ memory per sequence. It is a loan against memory to buy compute, and at realistic context lengths the interest is the whole cost of the system: thirty-two users at 4096 tokens hold 64 GiB of cache against 13.0 GiB of weights. The cache, not the model, sets batch size, and batch size sets throughput.

Worked micro-example. At $B=32$ the 32.0 GiB of cache traffic is 2.5 times the weight traffic. A 4-bit weight format cuts the step from 45.0 to 35.4 GiB, a 1.27-fold gain; halving $k$ cuts it to 29.0 GiB, 1.55-fold.

Drag sequence length until the cache bar overtakes the weights, then halve the head count and watch it quarter — that gesture is the argument for grouped-query attention.

Shrinking the cache: GQA and paged attention

Intuition. Share the notes between colleagues who need the same ones, and hand out storage by the room rather than by the wing.

Formal definition. Multi-query attention sets $n_{kv}=1$; grouped-query attention sets $n_{kv} = n_h/g$, so $k$ shrinks by exactly $g$. Separately, paged attention replaces per-sequence contiguous allocation with a pool of blocks of $s$ tokens addressed through a block table, so logical adjacency no longer implies physical adjacency; waste is at most $s-1$ slots per sequence.

Why it is built this way. They attack the two halves of the problem. GQA cuts per-token size at a small cost in expressiveness — query heads in a group cannot search keys for different things — and $g$ from 4 to 8 is measured to recover almost all of multi-head quality, while $g = n_h$ (MQA) is worse and now rare. Paging kills external fragmentation: reserving max_seq_len contiguously wastes 60 to 80 percent of memory on real traces, and that waste is what caps the batch.

Worked micro-example. With $g=4$, $k = 131{,}072$ bytes $= 128$ KiB, so at $B=32$, $T=2048$ the step moves 21.0 GiB in 11.1 ms instead of 45.0 GiB in 23.7 ms, and the freed pool allows roughly three times the batch. For paging, $s=16$ on a 4096-token sequence wastes at most 15 tokens — 7.5 KiB out of 2 GiB.

Continuous batching and the metrics that measure it

Intuition. A bus that waits until full and runs a fixed route, versus a taxi rank where the next passenger takes the seat the moment one frees.

Formal definition. Static batching runs $B$ requests until all finish, then forms the next batch; continuous, or iteration-level, batching re-decides composition every step. The metrics are time to first token $\text{TTFT}$ (queueing plus prefill), time per output token $\text{TPOT}$, $\text{E2E} = \text{TTFT} + (n-1)\text{TPOT}$, aggregate throughput, and goodput — the tokens/s delivered inside the latency SLO.

Why it is built this way. Output lengths are heavy-tailed, so under static batching a 50-step sequence occupies a slot for the 300 steps its slowest batch-mate needs, and since step cost barely changes with batch in the bandwidth-bound regime, every idle slot is straight loss. Goodput exists because "tokens per second" is unfalsifiable: serve one request at a time for excellent TPOT and terrible throughput, or batch maximally for the reverse.

Worked micro-example. Later, 200 requests with outputs uniform on $[50,300]$ give $4.99$ tokens per step and mean TTFT of 840 steps under static batching, against $6.62$ and 2.7 steps under continuous. An SLO of 2 s at $n=200$ allows $\text{TPOT} \le (2000-\text{TTFT})/199$; at $\text{TTFT}=300$ ms that is 8.5 ms, which the 23.7 ms step misses by 2.8-fold, and cutting the batch to 12 still misses at 12.3 ms — the lever is $k$, not $B$. Two refinements matter: chunked prefill caps prefill tokens per step so long prompts do not stall decoding, and preemption handles exhaustion by swapping blocks to host memory or dropping the cache and recomputing it on resumption.

Quantization

Intuition. Fewer bits per number means fewer bytes to fetch, and decode is a byte-fetching problem — but you must unpack before you multiply.

Formal definition. Symmetric absmax to $b$ bits: $s = \max_i|w_i|/(2^{b-1}-1)$, $\hat{w}_i = s\,\operatorname{round}(w_i/s)$, error at most $s/2$. Asymmetric (zero-point) spends one code on an offset so $[\alpha,\beta]$ need not straddle zero: $s = (\beta-\alpha)/(2^b-1)$, $z = \operatorname{round}(-\alpha/s)$, $\hat{w}_i = s(\operatorname{round}(w_i/s+z)-z)$. Group-wise applies either to blocks of 64 or 128, costing an fp16 scale per group — 4 bits at group 128 is really $4 + 16/128 = 4.125$ bits.

Why it is built this way. Quantization pays exactly when the kernel is bandwidth-bound and pays nothing when it is compute-bound, because tensor cores need 16- or 8-bit operands anyway. Hence int4 is a decode technology, not a prefill technology.

Worked micro-example. 13.0 GiB of bf16 weights become $7\times10^9 \times 4.125/8 = 3.36$ GiB, a 3.9-fold reduction — a 1.27-fold step-time gain at long context because the cache is untouched, and close to 3-fold at short context where weights dominate.

Drag the value and watch where it lands at each precision; the int4 error is relative to the *group maximum*, not the value, which is why group size matters.

The named methods attack different parts of this. GPTQ treats quantization as layer-wise least squares, minimising $\|\mathbf{W}\mathbf{X}-\hat{\mathbf{W}}\mathbf{X}\|_2^2$ on calibration activations: quantize one input channel at a time in fixed order, then push the error onto the channels not yet quantized using the damped inverse Hessian $\mathbf{H}^{-1}$ with $\mathbf{H} = 2\mathbf{X}\mathbf{X}^\top$. After quantizing column $j$, the error $e_j = (w_j-\hat{w}_j)/[\mathbf{H}^{-1}]_{jj}$ propagates as $\mathbf{W}_{:,j+1:} \to \mathbf{W}_{:,j+1:} - e_j[\mathbf{H}^{-1}]_{j,j+1:}$. AWQ observes that about 1 percent of weight channels carry disproportionate importance and that importance tracks activation magnitude rather than weight magnitude; it rescales per input channel, $\mathbf{W}' = \mathbf{W}\operatorname{diag}(\mathbf{s})$ with $\mathbf{X}' = \operatorname{diag}(\mathbf{s})^{-1}\mathbf{X}$, so the layer's function is unchanged while salient channels get finer relative resolution, and searches $\mathbf{s}_j = \bar{a}_j^{\beta}$ on a grid with no gradients, where $\bar{a}_j$ is channel $j$'s mean absolute activation. KV-cache quantization shrinks $k$ itself: keys carry outlier channels that persist across tokens, values carry outliers per token, so keys are quantized per channel and values per token. W4A16 stores weights at 4 bits and multiplies in bf16, cutting weight traffic but not the cache. GGUF/k-quants in llama.cpp target CPU, Metal and batch-of-one: super-blocks of 256 split into eight sub-blocks of 32, a 6-bit scale per sub-block, 16-bit scale and 8-bit minimum per super-block, plus importance-matrix calibration.

Spending idle FLOPs: FlashAttention, speculation, distillation, parallelism

Intuition. FlashAttention never writes the intermediates down; speculative decoding fills idle arithmetic units with a guess it later checks for free.

Formal definition. FlashAttention tiles attention so the $\mathbf{Q}\mathbf{K}^\top$ block is consumed in on-chip memory, accumulating the softmax with a running maximum $m$ and a running denominator $a$, $m_{\text{new}} = \max(m_{\text{old}},m_i)$ and $a_{\text{new}} = a_{\text{old}}e^{m_{\text{old}}-m_{\text{new}}} + a_i e^{m_i-m_{\text{new}}}$ — exact, not approximate, and the same recurrence lets FlashDecoding split the cache into per-SM chunks and merge them. Speculative decoding proposes $\gamma$ tokens from a cheap draft $q$, evaluates them in one target pass, and accepts each with probability $\min(1,p/q)$, replacing rejections from the normalised residual $(p-q)_+$. Distillation trains a student on the teacher's softened distribution, $\mathcal{L} = (1-\lambda)\mathrm{CE}(\mathbf{y},\mathbf{p}_S) + \lambda\tau^2\mathrm{KL}(\mathbf{p}_T^{\tau}\|\mathbf{p}_S^{\tau})$; the $\tau^2$ factor exists because gradients against soft targets scale as $1/\tau^2$, so without it raising $\tau$ to reveal dark knowledge shrinks the distillation term to nothing.

Why it is built this way. All three exploit slack. In prefill the slack is memory capacity — at $T=8192$ with 32 heads the score matrix is 134 MiB per head and nobody reads it back. In low-batch decode the slack is arithmetic throughput — the bus is saturated while the tensor cores idle, so FLOPs consuming bytes already in registers are nearly free. Tensor parallelism divides the weight bytes each device must read, which is why it helps throughput, and inserts an all-reduce of a $B\times T\times d$ activation per layer, which is why it can hurt latency at batch one.

Worked micro-example. With $\alpha = 0.8$, $\gamma = 4$, the expected tokens per target step is $(1-0.8^5)/0.2 = 3.36$; if the draft costs 5 percent of a step, the speedup is $3.36/(1+4\times0.05) = 2.8\times$. At high batch, once the step is compute-bound, verification is no longer free and the gain collapses.

The algorithm, step by step

One iteration of a continuous-batching engine.

  1. Drain completions. For every sequence that emitted end-of-sequence or hit max_tokens, stream its output, free its blocks, remove it from the batch.
  2. Schedule prefill. Walk the waiting queue in arrival order; admit request $i$ if len(free) >= ceil(plen/s) - owned and a slot is free, else preempt the lowest-priority running sequence or stop admitting.
  3. Budget the step. Cap new tokens per step across prefill chunks plus one decode token per running sequence, so no long prompt monopolises a step.
  4. Write block tables. Extend each sequence's block list from the free list in logical order, recording logical -> physical.
  5. Forward with paged attention. Resolve block indices through the table; take positions from the per-sequence counter, not the block index, so positions stay monotonic across non-contiguous blocks.
  6. Sample per sequence, applying each request's temperature, top-$p$, and seed to its own logit slice.
  7. Stream, detokenising incrementally and holding back incomplete multi-byte tokens.
  8. Record per-request timestamps for TTFT, TPOT, and goodput.

```text loop: for seq in finished(batch): free_blocks(seq); batch.remove(seq) while waiting and slots(batch) > 0: seq = waiting[0]; need = ceil(len(seq)/s) - len(seq.blocks) if free_blocks_count() < need: if can_preempt(batch): preempt(lowest_priority(batch)) else: break alloc(seq, need); batch.add(seq); waiting.pop() logits = model.forward(batch, paged_kv, block_tables) new = sample(logits, batch.sampling_params) stream(batch, new); append(batch, new); record_timings(batch) ```

Complexity. Per decode step, time is $O(2PB + \sum_i 4LT_in_{kv}d_h)$ FLOPs and $O(2P + B\bar{T}k)$ bytes, so wall-clock is $\max(\text{FLOPs}/F,\ \text{bytes}/W_{\text{HBM}})$ — in practice the second. Memory is $O(2P + \sum_i \operatorname{ceil}(T_i/s) s k)$. Per-token cost is linear in $P/T$.

Derivations

1. From the roofline to the maximum useful batch

Set $\mathrm{AI}_{\text{decode}} = r$ and solve for $B$:

$$ \begin{aligned} \frac{2PB}{2P + BTk} = r &\text{, so that } 2PB - rBTk = 2Pr \\ &\text{hence } B^{*} = \frac{2Pr}{2P - rTk}. \end{aligned} $$

A finite solution needs $rTk < 2P$. Since intensity rises monotonically toward $2P/(Tk)$, the necessary condition for any batch to reach the compute roof is

$$ \frac{2P}{Tk} > r . $$

On an A100, $2P/(Tk) = 14\times10^9/(2048 \times 524288) = 13.0$, far below $r = 153$; on an H100 ($r=295$) the gap widens. So no batch size reaches the ridge: this model never becomes compute-bound at 2048 tokens. That proves every worthwhile optimisation is a bytes optimisation and bounds what batching can ever buy.

2. Quantization noise

With range $[-\alpha,\alpha]$ and step $\Delta = 2\alpha/2^b$, round-to-nearest error is approximately uniform on $[-\Delta/2,\Delta/2]$:

$$ \begin{aligned} \mathbb{E}[e] &= 0, \\ \mathbb{E}[e^2] &= \frac{1}{\Delta}\int_{-\Delta/2}^{\Delta/2} e^2\,de = \frac{\Delta^2}{12}. \end{aligned} $$

For a full-scale sinusoid of amplitude $\alpha$ the signal power is $\alpha^2/2$, so

$$ \mathrm{SQNR} = 10\log_{10}(\alpha^2/2) - 10\log_{10}(\Delta^2/12) = 10\log_{10}(6\alpha^2/\Delta^2) = 10\log_{10}(1.5 \cdot 4^{b}) = 1.76 + 6.02\,b $$

in dB: 49.9 at 8 bits, 25.8 at 4. Two caveats: weights are roughly Gaussian with a long tail, so clipping at $\max|w|$ wastes range on outliers, and an MSE-optimal 4-bit grid clips well below the maximum. Those facts are what AWQ's channel scaling and GPTQ's error compensation exploit.

3. Why speculative decoding preserves the distribution

Draw $x\sim q$, accept with probability $\min(1,p(x)/q(x))$, and on rejection draw from $r(x) = (p(x)-q(x))_+ / Z$ with $Z = \sum_y (p(y)-q(y))_+$. Then, using $p - \min(p,q) = (p-q)_+$,

$$ \text{Pr}[\text{reject}] = 1 - \sum_y q(y)\min(1,p(y)/q(y)) = 1 - \sum_y \min(p(y),q(y)) = \sum_y (p(y)-q(y))_+ = Z, $$

so

$$ \text{Pr}[\text{output}=x] = \min(p(x),q(x)) + Z\cdot\frac{(p(x)-q(x))_+}{Z} = \min(p(x),q(x)) + (p(x)-q(x))_+ = p(x), $$

because $\min(a,b)+(a-b)_+ = a$. Each position is preserved independently and the draft depends only on the accepted prefix, so the sequence distribution is preserved. Acceptance is a run of Bernoulli successes:

$$ \mathbb{E}[\text{tokens}] = \sum_{i=0}^{\gamma}\text{Pr}[\text{at least } i] = \sum_{i=0}^{\gamma}\alpha^i = \frac{1-\alpha^{\gamma+1}}{1-\alpha}, $$

with the $i=\gamma$ term the always-produced correction token. Including relative draft cost $c$, speedup is $\frac{1-\alpha^{\gamma+1}}{(1-\alpha)(1+\gamma c)}$, maximised at finite $\gamma$ and vanishing as $\alpha \to 0$.

Implementation from scratch

A paged allocator plus a continuous-batching scheduler, stepping one decode at a time. No matmuls: the point is the memory and scheduling arithmetic, which is where the throughput comes from.

```python import math, random class PagedKVCache: def __init__(self, n_blocks, block_size, bpt): self.s, self.bpt = block_size, bpt self.free = list(range(n_blocks - 1, -1, -1)) # LIFO free list self.table, self.tokens = {}, {} # seq -> block ids / n tokens def _need(self, sid, extra): return math.ceil((self.tokens.get(sid, 0) + extra) / self.s) - len(self.table.get(sid, [])) def fits(self, sid, extra): return len(self.free) >= self._need(sid, extra) def grow(self, sid, extra): need = self._need(sid, extra) assert need <= len(self.free), "out of KV blocks" self.table.setdefault(sid, []).extend(self.free.pop() for _ in range(need)) self.tokens[sid] = self.tokens.get(sid, 0) + extra def release(self, sid): self.free.extend(self.table.pop(sid, [])) # blocks go back to the pool self.tokens.pop(sid, None) def simulate(reqs, n_blocks, mode="continuous", max_batch=8, block_size=16, bpt=512 * 1024, max_ctx=2048): """reqs: (id, arrival_step, prompt_len, output_len); one step = one decode.""" cache = PagedKVCache(n_blocks, block_size, bpt) pending, running = list(reqs), {} step = tokens = 0 peak = {"paged": 0.0, "naive": 0.0, "waste": 0.0} ttft = {} while pending or running: if mode == "continuous": # admit whenever a slot frees i = 0 while i < len(pending) and len(running) < max_batch: rid, arr, plen, olen = pending[i] if arr > step or not cache.fits(rid, plen): i += 1 continue cache.grow(rid, plen) # prefill reserves prompt blocks ttft[rid], running[rid] = step - arr, olen pending.pop(i) elif not running: # static: wait for a full drain for rid, arr, plen, olen in pending[:max_batch]: if not cache.fits(rid, plen): break cache.grow(rid, plen) ttft[rid], running[rid] = step - arr, olen pending = pending[len(running):] step += 1 # one decode step for rid in list(running): cache.grow(rid, 1) running[rid] -= 1 tokens += 1 if running[rid] == 0: cache.release(rid) del running[rid] res = sum(len(b) for b in cache.table.values()) * block_size * bpt use = sum(cache.tokens.values()) * bpt peak["paged"] = max(peak["paged"], res) peak["waste"] = max(peak["waste"], res - use) peak["naive"] = max(peak["naive"], max_ctx * bpt * len(running)) return dict(tps=tokens / step, util=tokens / (step * max_batch), ttft=sum(ttft.values()) / len(reqs), paged=peak["paged"] / 2**30, naive=peak["naive"] / 2**30, waste=peak["waste"] / 2**30) random.seed(7) reqs = [(i, i * 25, random.randint(64, 400), random.randint(50, 300)) for i in range(200)] for mode in ("static", "continuous"): r = simulate(reqs, n_blocks=8192, mode=mode) print(f"{mode:10s} tok/step={r['tps']:5.2f} util={r['util']:.2f} " f"TTFT={r['ttft']:6.1f} paged={r['paged']:.2f}G naive={r['naive']:.1f}G") for bs in (4, 64, 256): r = simulate(reqs, n_blocks=8192, block_size=bs) print(f"block={bs:3d} wasted={100*r['waste']/r['paged']:5.1f}% of cache") ```

What to expect. Deterministic under seed(7):

```text static tok/step= 4.99 util=0.62 TTFT= 839.7 paged=1.46G naive=8.0G continuous tok/step= 6.62 util=0.83 TTFT= 2.7 paged=1.73G naive=8.0G block= 4 wasted= 0.6% of cache block= 64 wasted= 11.4% of cache block=256 wasted= 34.2% of cache ```

Static batching wastes 38 percent of its slots and makes every request wait for the slowest batch-mate. The naive max_ctx reservation peaks at 8.0 GiB where paging peaks at 1.7 GiB. Paged mode peaks higher than static in absolute GiB here because it runs a larger effective batch — memory used, not saved.

Worked example

Capacity plan for one A100 80 GiB serving a Llama-2-7B-class model in bf16 at 2048-token average context, then the same model with $g = 4$.

Cache budget $80 - 15.0$ 65.0 GiB 65.0 GiB
$k$ per token $2Ln_{kv}d_hb$ 512 KiB 128 KiB

At \$2 per GPU-hour one A100 costs \$0.000556 per second, so cost per million tokens is $0.000556 \times 10^6 / 2900 \approx \$0.19$ — about \$0.77 for four GPUs behind a load balancer before hosting margin. Input tokens are far cheaper: the same device prefills 2048 tokens per 230 ms, of order \$0.00006 per million tokens of pure compute, a ratio near $10^3$ against decode at this batch. Providers quote nearer 4 to 1 because they price to the market, but the direction is not in doubt: output tokens are the expensive ones, and they are expensive because of bytes, not FLOPs. Two checks catch most bad plans: does the cache exceed the weights (if so, cache compression outranks weight compression), and does the throughput figure survive division by the batch size to give a per-user token rate?

Common misconceptions

"The KV cache makes inference faster"

It does the opposite to memory and only helps compute. Caching converts $O(T^2)$ attention into $O(T)$ while costing $O(T)$ memory per sequence, and at realistic context lengths fetching that memory is the bottleneck — the cache is five times the weights in the worked example.

"Bigger batch is free throughput"

Batch helps only until the bus saturates and always costs latency: TTFT grows because prefill competes for the device, TPOT grows because each step moves more cache bytes. If a TPOT budget exists, the maximum batch is derived from it. Optimising tokens per second while ignoring goodput produces a system that is fast and useless.

"4-bit quantization gives a 4x speedup"

Weight bytes fall 3.9-fold; nothing else does. The cache is untouched, unpacking costs ALU cycles, and fixed per-step overheads remain. At long context with a large batch the gain is 1.27-fold, at short context it approaches 3-fold, and on a compute-bound prefill it is approximately zero.

"FlashAttention speeds up inference"

It performs exactly the same FLOPs. What it removes is the $O(T^2)$ HBM traffic of the score matrix — decisive for prefill, nearly irrelevant for decode, where that matrix is a $1\times T$ vector. Decode benefits from FlashDecoding's split over the cache dimension, a parallelism fix for low-batch underutilisation, not an arithmetic fix.

"Speculative decoding changes the output distribution"

Not if acceptance and residual sampling are implemented as specified — the marginal at each position is exactly $p$. Implement it wrong, for instance by accepting whenever the draft argmax matches, and you have silently replaced your model with something sharper and less diverse, which surfaces later as a benchmark regression you cannot explain.

Exercises

Warm-up (check understanding)

1. Compute $k$ for a 13B model with $L=40$, $n_{kv}=40$, $d_h=128$, fp16, and the footprint at 8192 tokens.

Solution $k = 2\cdot40\cdot40\cdot128\cdot2 = 819{,}200$ bytes $= 800$ KiB per token; at 8192 tokens that is 6.25 GiB per sequence, so a 40 GiB budget holds six sequences at full context.

2. TTFT is 350 ms, TPOT is 20 ms, and the response is 500 tokens. What fraction of end-to-end latency is prefill?

Solution $\text{E2E} = 350 + 499\times20 = 10{,}330$ ms, so prefill is 3.4 percent. At long outputs decode dominates, which is why TPOT is the number users feel.

3. Why is a 4-bit model not four times faster at 32k context?

Solution One sequence holds $32768 \times 512\,\text{KiB} = 16$ GiB of cache against 13 GiB of weights, so at $B=8$ the cache is 128 GiB against 13 GiB and compressing weights by 4 changes step time by about 8 percent. The lever is $k$: GQA, KV quantization, or a shorter context.

Core (do the math)

4. On an H100 ($F=989$ TFLOP/s, $W_{\text{HBM}}=3350$ GB/s), can any batch make decode compute-bound for $P=7\times10^9$, $T=1024$, $k=512$ KiB? Give the maximum achievable intensity.

Solution $r = 989/3.35 = 295$ FLOP/byte, while the asymptote is $2P/(Tk) = 14\times10^9/(1024\times524288) = 26.1$. Since $26.1 < 295$, the denominator $2P - rTk$ is negative for every $B$: **no batch reaches the ridge**, and the maximum intensity is 26.1, eleven times below the roof.

5. With a 70 GiB cache budget, $T=8192$, $L=32$, $d_h=128$, fp16, compute the maximum batch for $n_{kv}=32$ and $n_{kv}=8$.

Solution $n_{kv}=32$: $k = 512$ KiB, so a sequence costs 4 GiB — 17 sequences. $n_{kv}=8$: $k = 128$ KiB, so 1 GiB — 70 sequences. One architectural choice buys 4.1 times the batch.

6. A 4-bit format uses group size 128 with an fp16 scale per group. Give the effective bits per weight and the compression ratio against fp16.

Solution $4 + 16/128 = 4.125$ bits, so $16/4.125 = 3.88\times$. Group size 64 gives 4.25 bits and $3.76\times$; the metadata is 3 percent of the payload at group 128, which is why group size is a knob rather than a free choice.

7. Draft acceptance is $\alpha=0.7$, $\gamma=3$, and the draft costs 8 percent of a target step. Compute expected tokens per step and the speedup.

Solution $(1-0.7^4)/0.3 = 2.533$ tokens per step; speedup $= 2.533/(1+3\times0.08) = 2.04\times$. At $\alpha=0.9$ the same setup gives 3.44 tokens and $2.77\times$ — speculation bets on the draft being *right*, not merely cheap.

Stretch (build or break it)

8. Add recompute-based preemption to the simulator: when the pool is exhausted, evict the largest-footprint running sequence, drop its blocks, and requeue it with its original prompt. Measure throughput and TTFT under n_blocks=512.

Hint Track a `remaining_prompt` field per sequence; on eviction free its blocks, increment a `chunk_done` counter, and re-admit later as if newly arrived. Throughput drops less than you expect while TTFT tail latency grows sharply, because preemption moves cost from the admitted set into the queue — exactly what admission control exists to manage.

9. Show that paged allocation with block size $s$ wastes at most $s-1$ slots per sequence, and give the expected waste when lengths are uniform on $[1,s]$.

Solution A sequence of length $T$ occupies $\operatorname{ceil}(T/s)\,s$ slots, so waste is $\operatorname{ceil}(T/s)\,s - T \in [0,s-1]$. For $T$ uniform on $[1,s]$ every sequence occupies one block, so waste is $s-T$ with expectation $(s-1)/2$ — 7.5 tokens at $s=16$, matching the measured 0.6 to 2.7 percent. For long sequences relative waste scales as $s/(2T)$.

10. Construct a workload where continuous batching loses to static batching on goodput, and name the mechanism.

Solution Strict 300 ms TPOT SLO, 16k-token prompts, 20-token outputs. Admitting a request requires a roughly 1.8 s prefill that blocks every decoding sequence and blows the SLO for all of them, while static batching clumps the prefill storms so decode windows stay clean. The mechanism is **prefill-decode interference**: continuous batching mixes a compute-bound workload with a latency-sensitive one in a single step. The fixes are chunked prefill and prefill/decode disaggregation.
