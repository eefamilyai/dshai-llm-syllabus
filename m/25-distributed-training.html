Distributed Training

Every parallelism scheme is a different answer to the same memory equation.

on this page

Why this module exists

A 7B-parameter model needs 112 GB before it stores a single activation, and no accelerator has that much. Everything that follows — ZeRO, tensor parallelism, pipeline parallelism, activation recomputation — is one equation being rearranged. Learn the equation and the zoo of named techniques collapses into five terms, each with a known owner and a known price in bandwidth. Skip it and "FSDP with TP=8 and PP=4" is a configuration incantation; learn it and you can derive the plan for an unfamiliar cluster on paper, predict the step time, and know in advance which of the five terms will run out first. M24 supplied the roofline that prices every one of these trades in bytes and FLOPs; this module spends it.

Prerequisites check

If you miss two or more, revisit M24 (first three) or M16 (last two).

  1. On an H100, how many FLOPs can the tensor cores execute in the time HBM takes to deliver one byte?
  2. What is the arithmetic intensity of a $4096\times4096$ bf16 matmul, and is it compute or memory bound?
  3. Why does a ring all-reduce move $2(N-1)/N \cdot S$ bytes per rank rather than $S$?
  4. Why is training compute conventionally estimated as $6N$ FLOPs per token?
  5. If you double the batch size and halve the number of steps, what happens to the number of tokens processed?
Answers 1. $\pi/\beta = 989.4/3.35 \approx 295$ FLOP per byte. That single ratio governs every trade in this module. 2. $I \approx 1365$ FLOP/byte, four times the ridge point, so compute bound — but only if it is tiled with an L2-resident super-tile. 3. Because it is a reduce-scatter of $N-1$ chunks followed by an all-gather of $N-1$ chunks, each of size $S/N$: $2(N-1)\cdot S/N$. 4. Forward is $2N$ per token (one multiply–add per weight per token), and backward is $4N$ (two matmuls of the same size, one for the input gradient and one for the weight gradient). 5. The number of tokens is unchanged: $2 \times \text{batch} \times (\text{steps}/2) = \text{batch} \times \text{steps}$. This is why batch size and step count trade off almost freely, and why the *global* batch is the quantity that matters for the learning rate.

Learning objectives

  • Write down the memory consumed by a training run as an explicit sum over parameters, gradients, optimizer states and activations, and evaluate it for any model and parallel layout.
  • Derive the per-rank communication volume of a ring all-reduce and use it to compute the fraction of step time spent communicating.
  • Explain what each ZeRO stage shards, give the per-GPU bytes for each, and state the communication each adds.
  • Derive the Megatron column-parallel/row-parallel split of a transformer block and place every all-reduce in the forward and backward graphs.
  • Derive the pipeline bubble fraction and compute the micro-batch count needed for a target efficiency.
  • Decide, for a stated model and cluster, whether to spend memory on activations, recomputation, or more devices, and justify it arithmetically.
  • Compute the optimal checkpoint interval from cluster MTBF and checkpoint cost.
  • Compose a complete parallelization plan (TP/PP/DP/ZeRO degrees, micro-batch, accumulation) for a stated run and predict its step time and peak memory.
  • Identify the three ways a distributed run can fail silently — non-deterministic replay, unbalanced pipeline stages, and a stale data loader — and prevent each.

Notation and conventions

Symbol Meaning
$P$ number of parameters
$N$ number of devices (GPUs) in the job
$s, b, h$ sequence length, micro-batch size (sequences), model hidden width
$L$ number of transformer layers
$a$ number of attention heads
$S$ size of the gradient buffer in bytes, $S = 2P$ in bf16

Bytes are counted in mixed precision throughout: bf16 copies at 2 bytes per parameter, fp32 master weights gradients and Adam moments at 4. The term "activation" means any tensor saved for the backward pass.

Core concepts

The memory wall: exactly what occupies VRAM

Intuition. A training step keeps four things alive at once: the weights (needed for the forward pass), the gradients (produced by the backward pass), the optimizer's memories of the last two steps (needed by Adam), and every intermediate activation the backward pass will need. The weights are the smallest of the four.

Formal definition. For each parameter, mixed-precision Adam holds:

Item Bytes/param Why it exists
bf16 weight (forward copy) 2 what the matmuls read
bf16 gradient 2 produced by backward, consumed by the optimizer
fp32 master weight 4 the bf16 weight is a rounded view; updates must not be
Adam first moment $m$ 4 exponential average of the gradient
Adam second moment $v$ 4 exponential average of the squared gradient
Total 16 $2+2+4+4+4$

So the model state alone is $16P$ bytes. Activations add $L \cdot A$ where, counting one tensor per saved intermediate in bf16 (layer-norm inputs and outputs, Q, K, V, the attention output, both MLP hidden activations, and the residual), a literal count gives

$$A \;\approx\; 36\,sbh \;+\; 4abs^2,$$

with the second term present only if the $s \times s$ attention matrix is materialised. The published Megatron accounting gives $34sbh + 5abs^2$ — a different bookkeeping of the same tensors, and the 5% disagreement is the point: the structure of the sum is what you must be able to write down, not the constant.

Why it is built this way. fp32 master weights exist because an update $\theta_{t+1} = \theta_t - \eta\, \hat{m}_t/(\sqrt{\hat{v}_t}+\epsilon)$ applied to a bf16 weight loses the update entirely when $|\eta\hat{m}/\sqrt{\hat{v}}| < 2^{-8}|\theta|$, which happens routinely for small learning rates and large weights. Saving activations exists because recomputing them costs a forward pass. Every design decision in distributed training is a choice about which of these five lines to shrink, and the answer is different for each line.

Worked micro-example. A 7B model: $16 \times 7\times10^9 = 112$ GB of state, against 80 GB on an H100. The model does not fit on one device even with zero activations. At $s = 4096$, $b = 8$ the activations are $36 \times 4096 \times 8 \times 4096 = 4.8$ GB per layer, or 155 GB over 32 layers — and the un-flashed attention term is $4abs^2 = 4 \times 32 \times 8 \times 4096^2 = 17$ GB per layer, 550 GB in total. Whether you keep the score matrix or not is a 4$\times$ difference in total memory.

Data parallelism: the all-reduce that makes it work, and why it stops

Intuition. Give every worker a complete copy of the model and a different slice of the data. Each computes a gradient on its own slice; average the gradients and everyone applies the same update. The workers never disagree, so it is exactly equivalent to one enormous batch.

Formal definition. With $N$ replicas and $B$ samples each, the update uses gradient

$$\mathbf{g} = \frac{1}{N}\sum_{i=1}^{N} \mathbf{g}_i,$$

which requires a reduce of $N$ buffers of $S = 2P$ bytes followed by a broadcast of the result — an all-reduce. Implemented as a ring, each rank sends $2(N-1)/N \cdot S$ bytes (derived in D1), so the per-rank volume is essentially $2S$ for large $N$.

Why it is built this way. Averaging gradients rather than models keeps the parameter update identical on every rank, so no divergence is possible and no locking is needed. The cost is that every rank must hold the complete model state, which is precisely what fails at 112 GB.

Worked micro-example. 7B in bf16 gradients: $S = 14$ GB. On 8 GPUs inside one node at 450 GB/s of unidirectional NVLink, the ring moves $2 \times \frac{7}{8} \times 14 = 24.5$ GB per rank, taking $24.5/450 = 54$ ms. Across nodes over 400 Gb/s InfiniBand (50 GB/s), the same all-reduce takes 490 ms. If a step's compute is 1.2 s, intra-node DP costs 4.5% of the step and cross-node DP costs 41%. That ratio, not any algorithmic property, is what forces hierarchical topologies and what makes "data parallel across 1024 GPUs" require very large batches.

Two refinements matter in practice. Gradient bucketing: instead of one all-reduce after the backward pass, bucket gradients by layer and start each bucket's all-reduce as soon as its backward is finished, overlapping communication with the remaining backward compute. The bucket size trades launch overhead (small buckets, many messages, latency-bound) against overlap window (large buckets, fewer messages, less overlap) — the usual sweet spot is 25–100 MB. no_sync: with gradient accumulation, run the all-reduce only on the last micro-batch, cutting DP communication by the accumulation factor at no cost.

Plain DP stops scaling for two independent reasons. Memory: it replicates $16P$ bytes per device, so it cannot fit a model that does not fit on one device. Bandwidth: the all-reduce is $O(S)$ per step, independent of batch, so as you add devices the batch must grow to keep the compute-to-communication ratio constant, and beyond a certain size the batch no longer helps convergence.

ZeRO: sharding the four things

Intuition. Data parallelism is wasteful in a specific way: every worker keeps a complete copy of a 112 GB state, but at any instant a worker is using only one of the four line items. Shard each line item across the workers and let them fetch what they need — the same computation, spread over the same memory, with a network bill.

Formal definition. ZeRO is a sequence of three shardings, applied to the memory equation's terms:

Configuration Bytes per param 7B on $N=8$ 7B on $N=64$ Comm per step
Plain DP $16$ 112 GB 112 GB $2S$
ZeRO-1: shard optimizer states $4 + 12/N$ 38.5 GB 29.3 GB $2S$
ZeRO-2: + shard gradients $2 + 14/N$ 26.3 GB 15.5 GB $2S$
ZeRO-3: + shard parameters $16/N$ 14.0 GB 1.75 GB $3S$

FSDP in PyTorch is ZeRO-3 restructured around module boundaries: it keeps parameters unsharded only for the duration of a layer's forward, all-gathering just-in-time and re-sharding immediately after, so peak memory is one layer's worth rather than the whole model's.

Why it is built this way. The three stages are ordered by how rarely the data is used. Optimizer states are touched once per step, so sharding them costs one extra communication per step. Gradients are touched once per step too but are produced incrementally, so they can be reduce-scattered during the backward pass, bucket by bucket, at no extra round trips. Parameters are touched on every forward and every backward of every micro-batch, so sharding them requires an all-gather in the critical path — which is why ZeRO-3 costs 1.5$\times$ the traffic of ZeRO-2 and why it is the last resort rather than the first.

Worked micro-example. 7B on 64 GPUs. Plain DP needs 112 GB per device — impossible. ZeRO-1 at $N=64$ gives $4 + 12/64 = 4.19$ bytes per parameter, 29.3 GB, which fits; but the activations of 155 GB do not, so activation recomputation is still required. ZeRO-3 gives 1.75 GB of state, freeing the entire budget for activations and enabling micro-batches 5–10$\times$ larger. Notice that no sharding reduces the activation term: that is the next four sections' job.

Tensor parallelism: splitting within a layer

Intuition. A single matmul can be cut two ways: give each worker a slice of the output columns (nobody needs anyone else's answer), or give each worker a slice of the input columns (everyone now needs everyone else's partial sum). The first is free, the second costs one all-reduce, and a transformer is built so that the two alternate.

Formal definition. For $\mathbf{Y} = \mathbf{X}\mathbf{W}$ with $\mathbf{W} \in \mathbb{R}^{d \times d'}$:

  • Column-parallel splits $\mathbf{W} = [\mathbf{W}_1 \mid \ldots \mid \mathbf{W}_N]$ along the output dimension. Rank $i$ computes $\mathbf{Y}_i = \mathbf{X}\mathbf{W}_i$ using the full $\mathbf{X}$. No communication during the matmul; the concatenated output is already correctly distributed.
  • Row-parallel splits $\mathbf{W} = [\mathbf{W}_1^\top \mid \ldots \mid \mathbf{W}_N^\top]^\top$ along the input dimension and requires $\mathbf{X}$ already split into $\mathbf{X}_i$. Rank $i$ computes $\mathbf{Y}_i = \mathbf{X}_i\mathbf{W}_i$, a partial sum, and

$$\mathbf{Y} = \sum_{i=1}^{N} \mathbf{Y}_i \quad \text{requires one all-reduce.}$$

Why it is built this way. Every transformer block decomposes into exactly two column→row pairs, and both work for a structural reason:

  • Attention. The QKV projection is column-parallel: heads are independent, and if you split $3d$ into $N$ slices of $3d/N$, each aligned to whole heads, rank $i$ owns $a/N$ heads outright. Attention over those heads needs no communication and no masking coordination. The output projection then consumes the head-concatenation, which is already split by head, so it is row-parallel by construction — one all-reduce.
  • Feed-forward. The first linear maps $d \to d_{ff}$ and is column-parallel; the activation is elementwise, hence also independent per slice; the second linear maps $d_{ff} \to d$ and is row-parallel — one all-reduce.

So the block needs exactly two all-reduces in the forward pass and two in the backward pass, and the activation stays sharded between them. Splitting anywhere else would need a communication per matmul.

Worked micro-example. $N = 8$, $h = 4096$, $s = 2048$, $b = 1$, bf16. Each all-reduce moves $2sbh$ bytes of activation, and a ring all-reduce costs each rank $\approx 2$ times the buffer, so the forward pass costs $2 \times 2 \times 2sbh = 8sbh = 8 \times 2048 \times 4096 = 67$ MB per layer. The layer's compute is 863 GFLOP, so each of 8 ranks performs 108 GFLOP, 109 $\mu$s at peak against 67 MB / 450 GB/s = 149 $\mu$s of NVLink time. The communication is larger than the compute, and both scale with the token count, so no batch size fixes the ratio. This is why TP is confined to the fastest links inside a node and why Megatron's kernels overlap the all-reduce of one block with the column-parallel GEMM of the next.

Pipeline parallelism: splitting between layers

Intuition. An assembly line. Each worker owns a contiguous block of layers and passes the activations to the next. No worker ever holds the whole model, and only the boundary tensor crosses the wire. The price is that during fill and drain, most of the line is idle.

Formal definition. With $p$ stages and $m$ micro-batches, a naive (GPipe) schedule takes $(m + p - 1)$ stage-times to complete $m$ micro-batches of work, so

$$\text{efficiency} = \frac{m}{m + p - 1}, \qquad \text{bubble fraction} = \frac{p-1}{m+p-1}.$$

Derived in D2. The 1F1B schedule keeps the same total but runs one forward and one backward per stage in a steady state, which reduces the memory of in-flight activations from $m$ to $p$ micro-batches — the bubble is unchanged, the footprint is not.

Why it is built this way. Pipeline parallelism is the only scheme whose communication volume is independent of both the model size and the batch size — it moves $2sbh$ bytes per micro-batch per stage boundary, no matter how big the model. That makes it the natural fit for slow inter-node links. Its cost is the bubble, which is why it is combined with gradient accumulation: the micro-batches that fill the pipeline are accumulation steps.

Worked micro-example. $p = 4$, $m = 16$: efficiency $16/19 = 84\%$, so 16% of every step is idle. To reach 90% you need $m \ge 9(p-1) = 27$ micro-batches, which at $s = 4096$ and 3 micro-batches per accumulation group means a long step. With virtual stages (each device holding $v$ non-contiguous chunks of layers, interleaved), the bubble becomes $(p-1)/(vm + p-1)$: $v = 2$ and $m = 16$ recovers efficiency $32/35 = 91\%$ at the cost of doubling the number of boundary sends.

Sequence and context parallelism

Intuition. Tensor parallelism shards everything in a layer except the parts that operate along the sequence — the norms, the residuals, the dropout. Those stay replicated, which is a waste of exactly the memory you were trying to save. So shard those along the sequence too.

Formal definition. In the tensor-parallel block, the layer-norm and residual tensors are replicated across TP ranks with shape $[s, b, h]$ even though the QKV projections are split. Sequence parallelism shards those along $s$: rank $i$ holds rows $i, i+N, \ldots$ (or a contiguous block), performs the norm on its shard, and the subsequent column-parallel GEMM does an all-gather that is now needed anyway.

Beyond a single layer, context parallelism applies the same idea to attention itself: split the sequence across devices so that each holds a slice of $\mathbf{Q}$ and must see all of $\mathbf{K}, \mathbf{V}$. Ring attention does this by circulating key/value blocks around a ring while each device computes its partial attention over the block it currently holds, using the online-softmax trick to accumulate across blocks. Because FlashAttention already streams over KV blocks, the block loop simply becomes a ring, and the communication overlaps with the compute almost completely.

Why it is built this way. Attention is the only operation whose cost grows with $s^2$, and its state — the KV cache — grows linearly with $s$ per sequence. At some context length, one sequence's cache exceeds a device's memory, and then no amount of TP/PP/DP helps because they shard the model, not the sequence.

Worked micro-example. For a 7B model ($L = 32$, $a = 32$, $d_h = 128$) the KV cache of a single 4096-token sequence is

$$2 \times L \times a \times s \times d_h \times 2\ \text{bytes} = 2 \times 32 \times 32 \times 4096 \times 128 \times 2 = 4.3\ \text{GB}.$$

At 128k tokens it is 137 GB — larger than the weights — for one sequence. Serving that requires the sequence itself to be distributed, which is exactly what context parallelism does.

Activation recomputation, decided by the roofline

Intuition. If an activation is cheaper to recompute than to store, do not store it. The question is "cheaper" in which currency — and the roofline converts both into seconds.

Formal definition. Storing an activation costs $B$ bytes of memory and saves $F$ FLOPs of recomputation. Recomputation is worth it when the time saved moving those bytes exceeds the time spent recomputing:

$$\frac{B}{\beta} > \frac{F}{\pi} \quad \text{ if and only if } \quad \frac{F}{B} < \frac{\pi}{\beta} = I_{\mathrm{ridge}}.$$

Recompute every tensor whose arithmetic intensity is below the ridge point. Full recomputation (store only each layer's input, $2sbh$ bytes) multiplies per-token FLOPs from $6N$ to $8N$ — a 33% compute tax — and reduces the activation term from $36sbh$ to $2sbh$ per layer, an 18$\times$ saving. Selective recomputation recomputes only the cheap-and-memory-hungry tensors (layer-norm outputs, the attention block's internals) and stores the outputs of the expensive matmuls, achieving most of the memory saving for a few percent of extra compute.

Why it is built this way. Because the trade is not symmetric: memory is per-device and finite, compute is per-device and parallel. You spend the resource that has slack. Since every elementwise and reduction op in a transformer has $I \approx 0.5$–1, recomputing them costs about 0.3% of the peak-time budget while saving 18$\times$ their memory.

Worked micro-example. 7B, $s = 4096$, $b = 8$: activations go from 155 GB to $32 \times 2sbh = 8.6$ GB. Per-token FLOPs go from $6N$ to $8N$, so the step takes 33% longer in a compute-bound regime. Trading 18$\times$ memory for 1.33$\times$ time is almost always correct, which is why every large run does it.

Fault tolerance and checkpointing

Intuition. At 1000 GPUs, something is broken almost all the time. A run is not a computation that occasionally saves state; it is a checkpointing loop that occasionally computes.

Formal definition. With cluster mean time between failures $T$ and checkpoint cost $\delta$, the fraction of time lost is $\delta/\tau$ (writing checkpoints) plus $\tau/(2T)$ (expected work lost per failure, half an interval on average). Minimising over $\tau$ gives Young's result:

$$\tau_{\mathrm{opt}} = \sqrt{2\delta T}.$$

Why it is built this way. The two terms pull in opposite directions and both are linear in $\tau$ or $1/\tau$, so the optimum is a square root, not a corner. Note the consequence: doubling the checkpoint size increases the optimal interval only by $\sqrt{2}$, so slow checkpointing is punished sub-linearly — which is why asynchronous checkpointing (copy to host memory, then write to disk in the background) is worth the complexity.

Worked micro-example. 64 GPUs with a per-GPU MTBF of 50,000 hours give $T = 50{,}000/64 = 780$ h $= 2.8\times10^6$ s. With $\delta = 30$ s (112 GB of optimizer state to a parallel filesystem), $\tau_{\mathrm{opt}} = \sqrt{2 \times 30 \times 2.8\times10^6} = 1.3\times10^4$ s, about 3.6 hours.

Three failure modes are silent rather than loud, and all three must be handled deliberately: non-deterministic replay (resume must restore RNG state, data-loader position, and any counter-based sampling, or the run quietly trains on a different distribution after every restart); stage imbalance (pipeline stages that do not have equal compute make the slowest stage the tick rate, and it shows up only as an unexplained 20% loss); and stale data (a resumed loader that restarts from epoch 0 leaks repeated data into the run).

The algorithm, step by step

The procedure below is what a training-infrastructure engineer does before launching anything. Its output is a plan: a tuple of degrees, a micro-batch size, an accumulation count, and a predicted step time and peak memory. If the prediction and the measurement disagree by more than 20%, the model of the machine (this module) is wrong somewhere and you find out on paper, not after three days of probing.

  1. Compose the memory sum. State bytes $= 16P$ (or $4P + 12P/N$ with ZeRO-1), activations $= L\,(36sbh + 4abs^2)$, buffers $\approx$ one bucket per layer, workspace for the largest GEMM.
  2. Compose the FLOP sum. Per token: $6N$ for training, $8N$ with full recomputation, plus $4\,\text{words}\cdot h \cdot a \cdot s$ for attention at sequence length $s$ — the last term is negligible until $s$ is large.
  3. Pick the tensor-parallel degree $N_t$: the largest that divides $a$ and $d_{ff}$, and whose measured all-reduce time is under a third of the layer compute time (D3). In practice $N_t = 8$ inside a node and never across nodes unless the model demands it.
  4. Pick the pipeline degree $N_p$: the smallest value that makes the state fit, because every stage adds a boundary and a bubble. Then check the bubble at the intended $m$ (D2).
  5. Set $N_d = N/(N_t N_p)$ for data parallelism, and verify the all-reduce fraction (D1) is acceptable.
  6. Choose the ZeRO stage that makes the residual state fit. Prefer the lowest stage that fits, since each stage costs bandwidth.
  7. Choose the micro-batch $b$ so the activation term fits with recomputation, then verify that the TP communication ratio is still acceptable.
  8. Set gradient accumulation $g$ to reach the target global batch: $B_{\text{global}} = b \cdot g \cdot N_d \cdot s$ tokens.
  9. Predict and check. Step time $= g\,\left(\text{FLOPs/token}\times b\cdot s\,/\,(\text{MFU}\cdot \pi \cdot N\right)$, and peak memory from step 1. If either is outside 20% of what you need, go back to step 3 with a different trade.

```text procedure PLAN(P, L, h, a, d_ff, N_gpus, link_gbps, per_gpu_mem): state_per_rank <- 16 * P / (Np * Nt) # ZeRO-3 assumption; recompute for lower stages acts_per_rank <- L * 2 * s * b * h / Nt # with full recomputation for Nt in [8, 4, 2, 1] where a % Nt == 0: # prefer the fastest interconnect for Np in divisors(N_gpus / Nt): for Nd in [N_gpus / (Nt * Np)]: if state_per_rank + acts_per_rank + slack > per_gpu_mem: continue t_comm_tp <- 8 * s * b * h * L / (link_gbps * 1e9) # forward all-reduces t_comp <- 6 * P * s * b * L / (mfu * peak_flops * Nt) if t_comm_tp > 0.33 * t_comp: continue return (Nt, Np, Nd, feasible) return INFEASIBLE # shrink the model or add devices ```

Cost. Steps 1–2 are $O(1)$ arithmetic; the search in step 3–5 enumerates at most a few dozen $(N_t, N_p)$ pairs; the whole plan is a spreadsheet, not a search. Its value is that every number in it can be checked independently against a measurement.

Derivations

D1. The ring all-reduce: $2(N-1)S/N$ bytes per rank

Step 1 — setup. $N$ ranks each hold an $S$-byte buffer. Split each buffer into $N$ chunks of $S/N$ bytes. Call rank $i$'s chunk $j$ as $c_i^{(j)}$.

Step 2 — reduce-scatter. In step $k = 1, \ldots, N-1$, rank $i$ sends chunk $(i-k) \operatorname{mod} N$ to rank $(i+1) \operatorname{mod} N$ and accumulates what it receives from rank $(i-1) \operatorname{mod} N$. After $N-1$ steps, rank $i$ holds the fully reduced version of chunk $(i - (N-1)) \operatorname{mod} N$ — exactly one chunk of the answer. Bytes sent by any rank during this phase: $(N-1) \cdot S/N$.

Step 3 — all-gather. In $N-1$ steps, circulate the reduced chunks the same way. Each rank sends $(N-1) \cdot S/N$ bytes and ends with all $N$ reduced chunks.

Step 4 — total. Per rank,

$$\text{bytes} = \frac{2(N-1)}{N}\,S \;\to\; 2S \text{ as } N \to \infty.$$

Step 5 — time. With $\gamma$ the per-rank link bandwidth and $\alpha$ the per-message latency,

$$T_{\text{ring}} = \frac{2(N-1)}{N}\cdot\frac{S}{\gamma} + 2(N-1)\alpha.$$

The payload term saturates at $2S/\gamma$: adding ranks does not increase the per-rank communication once the ring is large, which is the property that makes data parallelism scale at all. The latency term grows linearly, which is why small buffers must be bucketed.

Step 6 — evaluate. $S = 14$ GB, $\gamma = 450$ GB/s, $N = 8$: payload $= 24.5$ GB, $T = 54$ ms plus 14 latency hops (negligible at these sizes). The same buffer over 8 nodes of InfiniBand at 50 GB/s per rank: 490 ms.

D2. The pipeline bubble

Step 1 — timeline. Let $t$ be the time for one stage to process one micro-batch (assume a balanced pipeline). At clock 0, stage 1 starts micro-batch 1; stage 2 can start only at $t$, stage $p$ only at $(p-1)t$.

Step 2 — finish time. Stage $p$ finishes micro-batch 1 at $pt$. Micro-batch $m$ therefore finishes at $pt + (m-1)t = (p + m - 1)\,t$.

Step 3 — useful work. Each stage performs $m$ micro-batches of work, i.e. $mt$ of busy time, out of a wall-clock span of $(p+m-1)t$. Hence

$$E = \frac{m}{m+p-1}, \qquad \text{bubble} = 1 - E = \frac{p-1}{m+p-1}.$$

Step 4 — the micro-batch rule. Requiring a bubble below $\epsilon$:

$$\frac{p-1}{m+p-1} < \epsilon \;\text{ if and only if }\; m > \frac{(1-\epsilon)(p-1)}{\epsilon}.$$

For $\epsilon = 0.1$ this is $m > 9(p-1)$; a 4-stage pipeline needs 28 micro-batches to be 90% efficient.

Step 5 — interleaving. If each device instead owns $v$ discontiguous chunks of layers, it can work on a different chunk while another chunk's micro-batch is in flight, and the fill/drain cost is paid once per chunk rather than once per stage:

$$\text{bubble} = \frac{p-1}{vm + p-1}.$$

$v = 2$ halves the bubble, at the cost of $2\times$ the boundary sends and $2\times$ the activation storage per device.

Step 6 — why 1F1B matters even though the bubble is the same. GPipe's schedule runs all $m$ forwards, then all $m$ backwards: every device stores the activations of all $m$ micro-batches, $m \cdot 2sbh$ bytes. 1F1B interleaves one forward with one backward, so at steady state only $p$ micro-batches are in flight: $p \cdot 2sbh$ bytes. Same bubble, drastically less memory — the whole reason 1F1B was invented.

D3. Why tensor parallelism and data parallelism age differently

Step 1 — DP volume per step. $V_{\text{DP}} = 2S \approx 4P$ bytes per rank, independent of the batch.

Step 2 — TP volume per step. Per layer, four all-reduces (two forward, two backward) on buffers of $2sbh$ bytes, each costing $\approx 2$ buffers per rank:

$$V_{\text{TP}} = 4 \times 2 \times 2sbh \times L = 16\,s\,b\,h\,L\ \text{bytes per rank}.$$

Step 3 — divide by the compute on the same timescale. DP's $2S = 4P$ bytes are spent once per optimiser step, whose compute on one rank is $6P \cdot s b g N_d / N$. TP's $8sbh$ per layer are spent once per layer on one micro-batch, whose forward compute on one rank is $2P s b/(L N_t N_p)$. Converting bytes to time with $\gamma$ and FLOPs to time with $\pi$:

$$\rho_{\text{DP}} = \frac{2S/\gamma}{6P\,s\,b\,g\,N_d\,\pi^{-1}/N} = \frac{2}{3}\cdot\frac{\pi}{\gamma}\cdot\frac{N_t N_p}{s\,b\,g}, \qquad \rho_{\text{TP}} = \frac{8sbh/\gamma}{2P\,s\,b\,\pi^{-1}/(L N_t N_p)} = 4\cdot\frac{\pi}{\gamma}\cdot\frac{h\,L\,N_t N_p}{P}.$$

Step 4 — read the two formulas. $\rho_{\text{DP}}$ has the step's token count $s\,b\,g$ in its denominator: a bigger batch amortises data-parallel communication. $\rho_{\text{TP}}$ contains no batch term at all — it is fixed by the model's shape, the parallel degrees and the link speed. Doubling the global batch halves DP's relative cost and leaves TP's exactly where it was.

Step 5 — evaluate, 7B, $N_t = 8$, $N_p = 1$, $\gamma = 450$ GB/s, so $\pi/\gamma = 2198$. $\rho_{\text{TP}} = 4 \times 2198 \times 4096 \times 32 \times 8 / 7\times10^9 = 1.32$: at degree 8 the tensor-parallel all-reduces cost more than the layer's own compute, which is why they must overlap with it. With $s b g = 4096 \times 8 \times 5 = 164$k tokens per rank-step, $\rho_{\text{DP}} = \frac{2}{3} \times 2198 \times 8/164000 = 0.072$: 7% for the entire optimiser all-reduce.

Step 6 — the design rule. Put TP where the links are fastest and keep the degree as small as the model allows; grow DP with the batch, since that is the only knob that reduces its relative cost; use PP across the slowest links, since its volume is batch-independent and small. That ordering — TP within a node, PP across slow links, DP as large as the batch permits — is not a convention, it is what the two formulas say.

Implementation from scratch

The one algorithm in this module worth writing by hand is the ring all-reduce: it is short, it is the reason data parallelism scales, and its byte count is the basis of every communication estimate above. The code below runs all $N$ ranks in one process so you can print every hop; the assertion at the end checks it against np.sum.

```python # ring_allreduce.py — D1's protocol, verified. Ranks share one process for legibility. import numpy as np def ring_allreduce(buffers): """buffers: N arrays, rank i's copy of the same buffer. Returns (reduced, bytes/rank).""" N = len(buffers) bufs = [b.astype(np.float64).copy() for b in buffers] S = bufs[0].size assert S % N == 0, "the buffer must split into N equal chunks" chunk = S // N def sl(j): return slice(j * chunk, (j + 1) * chunk) sent = 0 # Phase 1, reduce-scatter: N-1 steps. At step k, rank i forwards chunk (i-k) % N # to rank (i+1) % N. Each rank ends up owning exactly one fully reduced chunk. for k in range(N - 1): out = [((i - k) % N, bufs[i][sl((i - k) % N)].copy()) for i in range(N)] for i in range(N): # all sends simultaneous: gather first j, data = out[i] bufs[(i + 1) % N][sl(j)] += data # accumulate, do not overwrite sent += data.nbytes / N # bytes moved by ONE rank # Phase 2, all-gather: N-1 steps. At step k, rank i forwards chunk (i-k+1) % N, # the chunk it received on the previous step, so reduced chunks circulate. for k in range(N - 1): out = [((i - k + 1) % N, bufs[i][sl((i - k + 1) % N)].copy()) for i in range(N)] for i in range(N): j, data = out[i] bufs[(i + 1) % N][sl(j)] = data # overwrite, do not accumulate sent += data.nbytes / N return bufs, sent if __name__ == "__main__": rng = np.random.default_rng(1) for N in (2, 4, 8): S = 8 * N * 64 data = [rng.normal(size=S) for _ in range(N)] reduced, moved = ring_allreduce(data) assert all(np.allclose(r, np.sum(data, axis=0)) for r in reduced) print(f"N={N}: {int(moved)} bytes/rank, formula 2(N-1)/N*S*8 = {2*(N-1)/N*S*8:.0f}") ```

What to expect. Every assertion passes, and the printed byte counts match $2(N-1)S/N$ to the byte: for $N = 4$ and $S = 2048$ fp64 elements that is $2 \times \frac{3}{4} \times 2048 \times 8 = 24{,}576$ bytes. Raise $N$ and watch the per-rank volume converge to $2S$ from below rather than grow — that plateau is the numerical reason data parallelism is viable at all.

Worked example

Goal: train a 7B model on 64 H100s (8 nodes of 8), target 40% MFU. Two plans, same hardware, computed before launch.

Plan A — the instinctive one. Tensor-parallel inside each node, pipeline-parallel across four groups of layers, data-parallel for the rest: $N_t = 8$, $N_p = 4$, $N_d = 2$.

Quantity Plan A Plan B
Parallel degrees TP 8 $\times$ PP 4 $\times$ DP 2 TP 8 $\times$ DP 8, ZeRO-1
State per GPU $16P/(8\cdot4) = 3.5$ GB $4P/8 + 12P/64 = 4.8$ GB
Activations per GPU 8 layers $\times 2sbh/8 = 0.27$ GB 32 layers $\times 2sbh/8 = 1.07$ GB
Peak memory $\approx 4$ GB of 80 $\approx 6$ GB of 80
Pipeline bubble ($m=5$) 37.5% 0%
DP all-reduce 1.75 GB/rank over IB, 35 ms 3.06 GB/rank over IB, 61 ms
Step compute (328k tokens) 0.544 s 0.544 s
Effective step 0.87 s 0.605 s
Throughput 376k tokens/s 542k tokens/s

Plan A is the plan most people write first, and it is 1.44$\times$ worse for one reason: the pipeline was solving a memory problem that sharding had already solved. With ZeRO-1 the whole 16-byte state fits 64 ways over, so the four stages exist only to create a 37.5% bubble. Plan B deletes them.

The numbers to notice:

  • State. $4P/N_t$ for the weights and gradients plus $12P/(N_t N_d)$ for the optimizer is 4.8 GB. Reducing the model to 70B: $4 \times 70\times10^9/8 + 12\times 70\times10^9/64 = 48$ GB per GPU — still fits, still without a pipeline. Pipeline parallelism enters only when the state stops fitting even with ZeRO-3, which for 80 GB parts is around the 300B-parameter mark.
  • The bubble is the whole difference. $m = 5$ micro-batches against $p = 4$ stages gives $(4-1)/(5+4-1) = 37.5\%$ idle. Raising $m$ to 28 would fix the efficiency but multiply the global batch by 5.6, which the learning rate may not tolerate.
  • Communication is not the bottleneck in either plan. 61 ms against 544 ms of compute is 11%, and gradient bucketing hides most of it inside the backward pass. The intuition that "distributed training is network-bound" is wrong at this scale; it is bubble-bound and memory-bound.

With Plan B in hand, the remaining decisions follow: micro-batch $b = 10$ sequences of 4096 tokens, $g = 1$, giving a 328k-token global step; a 32-way ZeRO-1 sharding of optimizer state; and a checkpoint every 3.6 hours by D1's sibling formula for $\tau_{\mathrm{opt}}$.

Common misconceptions

"Data parallelism distributes the model"

It distributes the data. Every rank holds a complete copy of the $16P$ state, which is why DP alone cannot train a model that does not fit on one device, and why the all-reduce exists at all.

"ZeRO-3 is strictly better than ZeRO-2"

ZeRO-3 costs 1.5$\times$ the communication of ZeRO-2 ($3S$ versus $2S$) and puts an all-gather of the parameters in the critical path of every forward pass. Use the lowest stage that fits, not the highest stage that exists.

"Tensor and pipeline parallelism are two ways to do the same thing"

They fail differently. TP communicates $8sbh$ bytes per layer on the fastest link and is batch-independent in relative cost; PP communicates $2sbh$ bytes per micro-batch per boundary on the slowest link and pays a bubble that grows with $p$. TP is limited by link bandwidth, PP by the number of micro-batches you can afford.

"More pipeline stages increase throughput"

Throughput per device scales as $m/(m+p-1)$. Adding a stage adds a device and a bubble; for fixed $m$ it can lower total throughput. Pipeline stages are a memory device, not a speed device.

"Activation checkpointing always costs a third of your speed"

Full recomputation turns $6N$ into $8N$ FLOPs, which costs 33% only in a compute-bound regime. A layer whose activation traffic already dominates loses nothing measurable, and a run that would otherwise OOM gains everything.

"A checkpoint lets you resume exactly"

Only if you also restore the RNG state, the data-loader position, and the optimizer's step counter. Most silent "resumed but slower" incidents are a loader that restarted at epoch 0, so the model saw the same documents again and the loss curve kinked without anyone noticing.

Exercises

Warm-up (check understanding)

1. Write out the 16 bytes per parameter and say which of them must be fp32 and why.

2. For $S = 2P$ and $N = 16$ ranks, how many bytes does one rank send in a ring all-reduce of a 13B model's gradients?

Solution **1.** bf16 weight (2), bf16 gradient (2), fp32 master weight (4), Adam $m$ (4), Adam $v$ (4). The master weight and both moments must be fp32 because the update $\eta\hat{m}/(\sqrt{\hat{v}}+\epsilon)$ is typically $10^{-3}$ to $10^{-4}$ relative to $\theta$; applied to a bf16 weight whose gap at $\theta$ is $2^{-8}|\theta|$, most updates would round to zero. **2.** $S = 2 \times 13\times10^9 = 26$ GB. Per rank $= 2(N-1)/N \cdot S = 2 \times \frac{15}{16} \times 26 = 48.75$ GB. As $N\to\infty$ this approaches $2S = 52$ GB, so going from 16 to 16,000 ranks changes the per-rank volume by 6%.

Core (do the math)

3. A 13B model with ZeRO-2 on 32 GPUs: how many bytes of state per GPU, and does it fit in 80 GB alongside 4 GB of activations?

4. A pipeline has $p = 6$ stages. How many micro-batches are needed for 90% efficiency, and what does that imply for the global batch if each micro-batch is 2 sequences of 4096 tokens?

5. Using $\rho_{\text{TP}} = 4(\pi/\gamma)hLN_tN_p/P$, compute the tensor-parallel communication ratio for a 7B on A100s ($\pi = 312$ TFLOP/s, $\gamma = 300$ GB/s) and on H100s, at $N_t = 8$. What does the difference say about why TP degrees grew more expensive over time?

Solution **3.** ZeRO-2 gives $2 + 14/N$ bytes per parameter $= 2 + 14/32 = 2.4375$, so $13\times10^9 \times 2.4375 = 31.7$ GB. Plus 4 GB of activations and ~2 GB of buffers: about 38 GB, which fits comfortably. **4.** $9(p-1) = 45$ micro-batches. At 2 sequences $\times$ 4096 tokens each, the global batch is $45 \times 2 \times 4096 = 368{,}640$ tokens. That is a large batch, which is why pipelines shorter than 6 stages are preferred: $p = 4$ needs only 27. **5.** $\pi/\gamma$ is $1040$ on A100 and $2198$ on H100. So $\rho_{\text{TP}}$ is $4 \times 1040 \times 4096 \times 32 \times 8/7\times10^9 = 0.62$ on A100 and $1.32$ on H100. Compute per byte of link bandwidth grew twice as fast as the link, so the same tensor-parallel degree became twice as expensive in relative terms — the arithmetic reason parallelism plans for the same model changed between hardware generations.

Stretch (build or break it)

6. You are given 512 H100s and a 70B model. Write a full plan (TP, PP, DP, ZeRO stage, micro-batch, accumulation) with a predicted peak memory per GPU and step time at 40% MFU, assuming 4k-token sequences.

7. Derive the maximum tensor-parallel degree a 7B model can use on 8 GPUs before the per-layer forward all-reduce exceeds the layer's forward compute, holding $h$, $L$ and $P$ fixed and treating $\pi/\gamma$ as a constant. Then explain why exceeding it is still sometimes correct.

8. Your 64-GPU run resumes from a checkpoint and the loss curve jumps upward for 300 steps before recovering. Give three distinct causes consistent with the memory equation and the failure modes in this module, and the check that distinguishes them.

Solution **6.** State per GPU with TP 8, DP 64, ZeRO-1: $4\times70\times10^9/8 + 12\times70\times10^9/(8\times64) = 35 + 1.64 = 36.6$ GB. Activations with full recompute at $b = 2$, all 32 layers, TP-split: $32 \times 2 \times 4096 \times 2 \times 4096/8 = 0.27$ GB, plus attention workspace. Peak $\approx 40$ GB of 80. Global batch $= b\,g\,N_d\,s = 2 \cdot g \cdot 64 \cdot 4096$; with $g = 2$ that is 1.05M tokens, and $\text{FLOPs} = 6 \times 70\times10^9 \times 1.05\times10^6 = 4.4\times10^{17}$, so at $0.4 \times 512 \times 989\times10^{12} = 2.02\times10^{17}$ FLOP/s the step takes 2.2 s. DP all-reduce: $S = 2P/N_t = 17.5$ GB, per rank $2 \times \frac{63}{64} \times 17.5 = 34$ GB over IB at 50 GB/s $= 0.69$ s — 31% of the step, so bucketed overlap is mandatory, or raise $g$. **7.** Setting $\rho_{\text{TP}} < 1$: $N_t < P/(4(\pi/\gamma)hL)$. For 7B on H100 that is $7\times10^9/(4\times2198\times4096\times32) = 6.1$, so degree 8 already exceeds it and degree 4 is the largest "free" one. Exceeding it is still correct when the model does not fit otherwise, and because the all-reduce after a row-parallel GEMM can overlap with the *next* block's column-parallel GEMM — the arithmetic cost is real but hideable. **8.** (a) *Stale data*: the loader restarted at epoch 0, so early documents were repeated; check by logging a hash of the first batch's token ids and comparing with the pre-crash log. (b) *RNG not restored*: dropout and any sampling-based data mixing reset; check by asserting the loss on a fixed held-out batch is bit-identical across the restart. (c) *Optimizer state*: the moments were saved in bf16 or the step counter reset, so the first updates are mis-scaled by $1/(1-\beta_1^t)$; check by comparing the first post-restart update norm with the pre-crash average. All three produce a transient bump; only the hash check identifies which.

Self-test

  1. What are the five components of the 16 bytes per parameter?
  2. Which ZeRO stage shards gradients, and what does sharding them cost in communication?
  3. Why is the row-parallel split — not the column-parallel one — the one that needs an all-reduce?
  4. Give the pipeline efficiency formula and its value for $p = 4$, $m = 12$.
  5. Which activation term does sequence parallelism reduce, and which does context parallelism reduce?
  6. State the recomputation decision rule in terms of arithmetic intensity.
  7. What is the optimal checkpoint interval when $\delta = 60$ s and the cluster MTBF is 500 hours?
Answers 1. bf16 weight, bf16 gradient, fp32 master weight, Adam first moment, Adam second moment: $2+2+4+4+4$. 2. ZeRO-2. It costs nothing extra in bandwidth — $2S$ either way — because gradients are produced incrementally and can be reduce-scattered during the backward pass. 3. Because row-parallel splits the *input* dimension, so each rank computes a partial sum that must be added across ranks; column-parallel gives each rank a disjoint slice of the output. 4. $m/(m+p-1) = 12/15 = 80\%$. 5. Sequence parallelism reduces the replicated $sbh$ terms (layer-norms, dropout, residuals) inside a tensor-parallel block; context parallelism reduces the $s^2$ attention term and the per-sequence KV cache. 6. Recompute when $F/B < \pi/\beta$ — that is, when the tensor's arithmetic intensity is below the ridge point, so the memory it saves costs more time than recomputing it. 7. $\tau_{\mathrm{opt}} = \sqrt{2\delta T} = \sqrt{2 \times 60 \times 1.8\times10^6} = 1.47\times10^4$ s $\approx 4.1$ hours.
