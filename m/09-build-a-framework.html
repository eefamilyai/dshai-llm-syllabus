Building Your Own Deep Learning Framework

Six stages from a scalar autograd engine to a trained character-level language model.

on this page

Why this module exists

You can use PyTorch for years and still be unable to answer basic questions about what it did: where the graph lives, why memory grows during the forward pass, why zero_grad exists, what torch.compile changed, and why a broadcast in the forward pass requires a sum in the backward pass. Reading the source does not fix this, because the source is optimized for speed and generic over dtypes, devices, and dispatch. Writing a small one does fix it: about 250 lines of NumPy will give you a working autodiff engine, module system, two optimizers, a training loop, and a character-level language model that fits a corpus to 0.03 bits per character. After that, the framework you use stops being a black box and becomes an implementation of something you have built.

Notation and conventions

Term Meaning here
data the NumPy array holding a node's value
grad $\partial\mathcal{L}/\partial\text{data}$, same shape as data, None until first written
_parents the nodes this node was computed from
_backward a closure that pushes this node's grad into its parents' grad
vjp the cotangent-to-cotangent function of one primitive
$B$ batch size
$C$ context length (characters of history)
$V$ vocabulary size
$d$ embedding width
bits/char $\mathcal{L}/\ln 2$ for a natural-log cross-entropy, i.e. $\log_2$ perplexity per character

Two conventions carried from M07: gradients are accumulated, never assigned, and backward() seeds the output's gradient with ones. One convention new here: grad is None rather than a zero array until something writes to it, which is how a real framework avoids allocating zeros for every intermediate tensor.

Core concepts

What a tensor actually needs to store

(1) Intuition. A tensor in a framework is three things at once: an array of numbers, a slot for its gradient, and a recipe for how to pass a gradient to whatever produced it. The numbers are the easy part; the recipe is the whole design.

(2) Formal definition. A minimal node is

$$ \text{node} = \left(\underbrace{\mathbf{a}}_{\text{data}},\ \underbrace{\bar{\mathbf{a}}}_{\text{grad}},\ \underbrace{\{v : v \to \text{node}\}}_{\text{parents}},\ \underbrace{\text{vjp}}_{\text{closure}}\right), $$

where the closure, when called, reads node.grad and adds the appropriate cotangent into each parent's grad. Five fields and no more: the graph is fully reconstructed from parents, and the mathematics lives entirely in the closures.

(3) Why it is built this way. Because it separates what was computed from how to differentiate it. The node needs no knowledge of the graph, and the graph needs no knowledge of calculus. Adding an operation means writing one closure; adding a container (sparse, quantized, distributed) means changing one class and nothing else.

(4) Worked micro-example. For c = a * b with a = 2.0, b = 3.0, the node holds data = 6.0, grad = None, parents = (a, b), and a closure that does a.grad += b.data * c.grad; b.grad += a.data * c.grad. With c.grad = 1 that yields a.grad = 3.0 and b.grad = 2.0, which is exactly $\partial c/\partial a = b$ and $\partial c/\partial b = a$.

define-by-run: the graph is byproduct, not blueprint

(1) Intuition. There are two ways to build an autodiff system. You can record a blueprint of the computation before running it (define-and-run, a tape), or you can let the computation create the graph as it runs (define-by-run). PyTorch is the second; the graph exists only as long as its tensors do.

(2) Formal definition. In define-by-run, every operation allocates a node and records its parents; the graph is a byproduct of the forward pass and can differ on every call. In tape-based systems (Theano historically, JAX's grad over traced functions), the function is traced once into a static graph that is then differentiated and, usually, compiled.

(3) Why it is built this way. Define-by-run makes control flow trivial: if and while and data-dependent recursion are just Python, and each execution gets the graph it actually used. That is why it fits RNNs with variable-length inputs and any model with data-dependent depth. The cost is that the graph is rebuilt every step, and that the interpreter overhead — Python-level node creation — can dominate small operations. Compilation exists to recover that cost.

(4) Worked micro-example. A forward pass with a data-dependent branch

```python h = layer1(x) if h.data.mean() > 0: # the graph differs on different batches h = layer2(h) ```

is impossible to express as a single static graph without a control-flow primitive, and trivial in define-by-run. This is the design decision, stated as one line of code.

Step through a tiny network one node at a time, forward then backward. Watch the order the nodes are visited: it is not the order they were created but a reverse topological order, and the interactive version makes it obvious why a node cannot fire before everything downstream of it has.

Broadcasting and the reduction it forces

(1) Intuition. Broadcasting is a lie told for convenience: when you add a bias of shape $(m,)$ to a batch of shape $(n,m)$, the forward pass pretends there are $n$ copies of the bias. The backward pass has to undo the lie, and undoing a copy is summing.

(2) Formal definition. If an operand of shape $\mathbf{s}$ is broadcast to shape $\mathbf{S}$, then

$$ \bar{\mathbf{a}} = \operatorname{reduce}_{\mathbf{s}}\!\left(\bar{\mathbf{c}}\right), \qquad \operatorname{reduce}_{\mathbf{s}}(\mathbf{G}) = \text{sum } \mathbf{G} \text{ over leading axes until } \mathrm{ndim} = |\mathbf{s}|, \text{ then over axes where } s_i = 1 \text{ and } S_i > 1 . $$

(3) Why it is built this way. Because the forward operation really did use $n$ copies of $\mathbf{b}$, each contributing a separate path from $\mathbf{b}$ to the loss, and the chain rule sums over paths. A framework that returns the unreduced gradient has the wrong shape and silently broadcasts that too, producing a plausible but incorrect answer — one of the most common bugs in hand-written backprop.

(4) Worked micro-example. $\mathbf{C}=\mathbf{A}+\mathbf{b}$ with $\mathbf{A}\in\mathbb{R}^{3\times4}$, $\mathbf{b}\in\mathbb{R}^4$: $\bar{\mathbf{A}}=\bar{\mathbf{C}}$ (shape preserved) and $\bar{\mathbf{b}}=\mathbf{1}^\top\bar{\mathbf{C}}\in\mathbb{R}^4$. If instead $\mathbf{b}\in\mathbb{R}^{1\times4}$ and $\mathbf{C}$ is $(3,4)$, the reduction must use keepdims=True to return $(1,4)$. And for a scalar b (shape ()), the reduction is a full sum to a scalar. The code below handles all three by construction.

Modules, parameters, and why ownership matters

(1) Intuition. A layer is a small object that owns parameters and knows how to map inputs to outputs. A model is a tree of such objects. The framework's job is to walk that tree and hand you the complete parameter list — complete being the operative word.

(2) Formal definition. A Parameter is a Tensor that is meant to be optimized. A Module is an object with named submodules and named parameters; parameters() returns the concatenation of its own parameters and those of its submodules, recursively. Optimizers receive that flat list once, at construction.

(3) Why it is built this way. Because the flat list is the interface between the model and the optimizer: the optimizer never asks the model anything again, which is what allows it to be implemented as a pure state machine. The failure mode is equally specific: if a submodule is stored in a plain Python container that the traversal does not know about (a list of layers, a dict of heads), its parameters are invisible to parameters(), the optimizer never updates them, and the model trains partially — the worst kind of bug, because the loss still goes down.

(4) Worked micro-example. The bug, in full: self.layers = [Linear(4,4), Linear(4,4)] makes parameters() return [], because a list is not a Module. The fix is one line in the container's constructor that registers each child, and it is the difference between a model that learns and a model that does not. The code in this module's Sequential does exactly that, and it is the bug I hit first when building it.

Optimizers as state machines

(1) Intuition. An optimizer holds one array per parameter and updates it when told to. Nothing more: it never sees the model, never sees the data, and never sees the loss.

(2) Formal definition. SGD with momentum holds a velocity buffer $\mathbf{v}$ per parameter: $\mathbf{v}\leftarrow\beta\mathbf{v}+\mathbf{g}$, $\boldsymbol{\theta}\leftarrow\boldsymbol{\theta}-\eta\mathbf{v}$. AdamW holds two buffers and a step counter:

$$ \mathbf{m}\leftarrow\beta_1\mathbf{m}+(1-\beta_1)\mathbf{g}, \quad \mathbf{v}\leftarrow\beta_2\mathbf{v}+(1-\beta_2)\mathbf{g}^2, \quad \boldsymbol{\theta}\leftarrow\boldsymbol{\theta}-\eta\left(\frac{\hat{\mathbf{m}}}{\sqrt{\hat{\mathbf{v}}}+\epsilon}+\lambda\boldsymbol{\theta}\right), $$

with $\hat{\mathbf{m}}=\mathbf{m}/(1-\beta_1^t)$ and $\hat{\mathbf{v}}=\mathbf{v}/(1-\beta_2^t)$ correcting the zero initialization.

(3) Why it is built this way. The bias correction exists because $\mathbf{m}$ and $\mathbf{v}$ start at zero, so the first few steps would be scaled by $(1-\beta_1^t)$ and $(1-\beta_2^t)$ — near zero for $\beta_2=0.999$ and $t=1$. Without correction the first steps are effectively zero-sized; with it, the first step is a sign-like step of size $\eta$. Weight decay is written outside the adaptive denominator (AdamW) rather than inside the gradient (Adam+L2), because inside it gets scaled by $1/\sqrt{\hat{\mathbf{v}}}$, making the effective decay depend on the gradient magnitude — exactly the coupling that decoupled decay removes.

(4) Worked micro-example. At $t=1$ with $\mathbf{g}=0.5$, $\beta_1=0.9$, $\beta_2=0.999$: $\mathbf{m}=0.05$, $\mathbf{v}=0.00025$, so $\hat{\mathbf{m}}=0.5$ and $\hat{\mathbf{v}}=0.25$, giving a step of $\eta\cdot0.5/(0.5+10^{-8})\approx\eta$ — a full-size step in the gradient's direction regardless of its magnitude. That scale invariance is what makes Adam's learning rate transferable across parameters, and what breaks it when you mix it with L2 in the gradient.

The training loop's four invariants

(1) Intuition. Four lines in a training loop are not bookkeeping; each one prevents a specific silent failure.

(2) Formal definition and the failure each prevents.

  1. Zero the gradients before the backward pass. Without it, step $t$'s gradient is the sum of steps $1..t$, and the effective learning rate grows without bound. Failure mode: loss falls, then oscillates, then diverges, with a gradient norm that grows monotonically.
  2. Set train/eval mode. Dropout and batch norm behave differently in each (M08). Failure: evaluation reports the training-mode loss, which is both optimistic and noisy.
  3. Disable graph construction during evaluation. Under define-by-run, evaluating with gradients enabled builds a graph you never use, so validation memory grows like a training step. Failure: out-of-memory during evaluation, often at exactly the point where the model got large enough to matter.
  4. Clip gradients before the step, and check finiteness. A single bad batch can produce a gradient 100× the typical norm and destroy an hour of training. Failure: a loss spike from which the model never recovers.

(3) Why it is built this way. Because all four failures are silent at first and expensive later. Each invariant is one line and is far cheaper than the debugging session it prevents.

(4) Worked micro-example. With gradients of norm 2.0 arriving every step and a learning rate of $10^{-3}$, forgetting to zero gives effective steps of $2, 4, 6, \ldots$ — the update size grows linearly in the step number, so by step 100 the model is moving 200× as far per step as it should. That trajectory always ends the same way.

The algorithm, step by step

The build order is chosen so that every stage is testable before the next one exists.

  1. Scalar engine. Value with data, grad, _parents, _backward; operator overloading for +, *, tanh, log, relu; backward() that sorts the graph topologically and runs the closures in reverse.
  2. Vectorize. Replace float with ndarray, add the reduction in every broadcasting vjp, add matmul, reshape, sum, __getitem__, and a fused softmax_cross_entropy. The engine's backward() does not change at all.
  3. Modules. Parameter(Tensor), Module with named parameters and submodules, Linear, ReLU, Sequential, Embedding. The only new idea is the recursive parameters() traversal.
  4. Optimizers. SGD with momentum, AdamW. Each holds one or two arrays per parameter, plus a step counter for Adam.
  5. Training loop. Batching, zeroing, backward, clipping, step, periodic evaluation, logging.
  6. Models. First XOR with a 2-8-2 MLP, then a character-level language model: embedding, flatten, hidden layer, vocabulary logits, cross-entropy, and a sampling loop.

```text backward(root): order = topological_sort(root) # DFS postorder root.grad = ones_like(root.data) for node in reversed(order): node._backward() # push grad into each parent, accumulating topological_sort(root): seen, order = {}, [] visit(v): if v not in seen: mark; visit(p) for p in v._parents; append(v) visit(root); return order ```

Complexity. A backward pass costs about twice a forward pass in FLOPs and needs the forward values to be retained, so time per step is $O(3\cdot\text{forward})$ and memory is $O(\text{forward activations})$ (M07). The engine's own overhead — allocating nodes and pushing gradients — is $O(\#\text{nodes})$ per pass, which is why a real framework fuses operations and why torch.compile exists: at small tensor sizes this overhead, not arithmetic, is the bottleneck.

Derivations

1. The broadcasting vjp, in general

Let $\mathbf{c} = f(\mathbf{a},\mathbf{b})$ where the forward operation is elementwise but the operands have different shapes and NumPy broadcasts them to a common shape $\mathbf{S}$. Broadcasting means each operand is first expanded: $\tilde{\mathbf{a}}$ of shape $\mathbf{S}$ with

$$ \tilde a_{i_1\ldots i_k} = a_{j_1\ldots j_m}, \qquad j_r = \begin{cases} i_r & \text{if } a \text{ has an axis here}, \\ 1 & \text{otherwise (axis was inserted)},\end{cases} $$

and axes where $a$ had size 1 are replicated. Since $\mathbf{c}$ depends on $\mathbf{a}$ only through $\tilde{\mathbf{a}}$, the chain rule gives

$$ \bar a_{j_1\ldots j_m} = \sum_{\text{all } i \text{ mapping to } (j_1,\ldots,j_m)} \bar c_{i_1\ldots i_k} \cdot \frac{\partial \tilde a}{\partial a}, $$

and $\partial\tilde a/\partial a = 1$ for every copy, so the vjp is exactly a sum over the axes that were inserted or replicated. Concretely, with $\mathbf{G}=\bar{\mathbf{c}}$:

$$ \bar{\mathbf{a}} = \sum_{\text{inserted leading axes}} \mathbf{G} \quad\text{then}\quad \sum_{i:\, s_i = 1,\, S_i > 1} \mathbf{G}\ \text{along axis } i \text{ with keepdims}. $$

Three cases, with shapes:

forward shapes $\bar{\mathbf{a}}$ $\bar{\mathbf{b}}$
$\mathbf{A}+\mathbf{b}$ $(3,4)+(4,)$ $\mathbf{G}$ $\sum_{i=1}^{3}G_{ij}$, shape $(4,)$
$\mathbf{A}+b$ $(3,4)+()$ $\mathbf{G}$ $\sum_{i,j}G_{ij}$, shape $()$
$\mathbf{A}+\mathbf{B}$ $(3,1,4)+(2,4)$ $\sum_{i=1}^{2}G_{ij}$, shape $(1,4)$... reduced to $(3,1,4)$ by summing over the replicated axis then re-adding the size-1 axis $\sum_{i=1}^{3}G_{ij}$, shape $(2,4)$

The implementation is six lines, and the keepdims=True in the second loop is not cosmetic: it preserves the rank so that the assignment self.grad += ... keeps the original shape.

2. Matmul vjps

Let $\mathbf{Z}=\mathbf{X}\mathbf{W}$ with $\mathbf{X}\in\mathbb{R}^{n\times k}$, $\mathbf{W}\in\mathbb{R}^{k\times m}$, so $Z_{ij}=\sum_{p}X_{ip}W_{pj}$. For the input,

$$ \bar X_{ip} = \sum_{i',j}\bar Z_{i'j}\frac{\partial Z_{i'j}}{\partial X_{ip}} = \sum_{j}\bar Z_{ij}W_{pj} = \left(\bar{\mathbf{Z}}\mathbf{W}^\top\right)_{ip}, $$

and for the weight,

$$ \bar W_{pj} = \sum_{i,i'}\bar Z_{i'i}\frac{\partial Z_{i'i}}{\partial W_{pj}} = \sum_{i}\bar Z_{ij}X_{ip} = \left(\mathbf{X}^\top\bar{\mathbf{Z}}\right)_{pj}. $$

Both are matmuls of the same asymptotic cost as the forward one; that factor of two per layer is the whole of the "backward costs twice forward" rule.

3. Why reverse topological order is required

Claim. If a node's closure runs before all of its children (nodes it feeds) have completed, the gradient it propagates is missing contributions.

Proof. The adjoint of $v$ is $\bar v=\sum_{u\in\text{children}(v)}\bar u\,\partial u/\partial v$ (M07, §4). Each term requires the final value of $\bar u$, which is only available after every child of $u$ has pushed into it. Take any linear extension of the DAG that is not a reverse topological order: it contains an edge $(v,u)$ with $v$ processed before $u$. When $v$'s closure runs, $\bar u$ may still be missing the contributions from $u$'s own children, so the term $\bar u\,\partial u/\partial v$ is added with an incomplete $\bar u$ and the final $\bar v$ is wrong. Conversely, reverse topological order guarantees by induction that when $v$ is processed, every child $u$ has already received all of its contributions, so each $\bar u$ is final. $\blacksquare$

The DFS postorder in topological_sort produces exactly such an order, and the reversal in backward() is the only place the ordering is used.

4. Accumulation, and why a per-node "visited" flag is not enough

A node can be reached from the output by many paths (reuse of a parameter, a residual stream read twice, a shared embedding). Each path contributes a term to the adjoint, and the multivariable chain rule sums them. The engine therefore writes += into grad and initializes grad lazily to zeros on first write. Contrast this with a forward-mode implementation, where the same node may also be reached once per tangent direction: forward mode accumulates tangents the same way, so the "sum over paths" structure is common to both modes — only the direction differs.

Deduplicating the traversal (a seen set used to skip nodes) would be correct for a DAG only if it skipped re-visiting a node rather than re-accumulating into it. Confusing the two produces gradients that are correct for trees and silently wrong for DAGs, which is precisely the case every real network is in.

5. Why the fused softmax plus cross-entropy is worth writing by hand

The composed computation is $\mathcal{L}=-\log p_y$ with $p=\operatorname{softmax}(\mathbf{z})$, and by M06's Jacobian and M07's cancellation,

$$ \frac{\partial\mathcal{L}}{\partial z_j} = p_j - y_j . $$

For a batch, $\bar{\mathbf{Z}}=(\mathbf{P}-\mathbf{Y})/n$. Implementing it as one node rather than three has two consequences. First, stability: the forward pass subtracts the row maximum, $\tilde z_j=z_j-\max_kz_k$, so every exponent is $\le1$ and $\exp$ cannot overflow; and since $\operatorname{softmax}(\mathbf{z}+\mathbf{c}\mathbf{1}^\top)=\operatorname{softmax}(\mathbf{z})$ exactly, the subtraction changes nothing but the floating-point behaviour. Second, cost and precision: composing log(softmax(z)) computes $\log$ of a number that may round to exactly $0$ for a confident wrong prediction, producing $-\infty$ and a NaN gradient; the fused version never materializes $p$ inside a logarithm, and the gradient $p-y$ is bounded in $[-1,1]$ regardless of the logits. This is why every framework fuses the pair, and why the fused version is the right thing to hand-write first.

Implementation from scratch

Six stages, each runnable before the next exists. Every line below is from a working program: the outputs quoted are what the code actually prints.

Stage 1 — the scalar engine

This is M07's engine, extended with relu and log, and it is the whole idea with the tensors taken out.

```python import math class Value: def __init__(self, data, parents=()): self.data = float(data); self.grad = 0.0 self._parents = parents; self._backward = lambda: None def __add__(self, o): o = o if isinstance(o, Value) else Value(o) out = Value(self.data + o.data, (self, o)) def b(): self.grad += out.grad; o.grad += out.grad out._backward = b; return out def __mul__(self, o): o = o if isinstance(o, Value) else Value(o) out = Value(self.data * o.data, (self, o)) def b(): self.grad += o.data * out.grad; o.grad += self.data * out.grad out._backward = b; return out def relu(self): out = Value(max(0.0, self.data), (self,)) def b(): self.grad += (1.0 if self.data > 0 else 0.0) * out.grad out._backward = b; return out def log(self): out = Value(math.log(self.data), (self,)) def b(): self.grad += out.grad / self.data out._backward = b; return out def __neg__(self): return self * -1.0 def __sub__(self, o): return self + (-o if isinstance(o, Value) else -o) def __radd__(self, o): return self + o def __rmul__(self, o): return self * o def backward(self): topo, seen = [], set() def build(v): if id(v) in seen: return seen.add(id(v)) for p in v._parents: build(p) topo.append(v) build(self) self.grad = 1.0 for v in reversed(topo): v._backward() ```

Three things to notice before moving on: grad starts at 0.0 rather than None (simpler for scalars), the closures capture out and the operands by closure rather than storing them as attributes, and nothing in backward() knows what the operations were.

Stage 2 — vectorize, with the reduction

The engine does not change; only the containers do. grad becomes lazily allocated, and every broadcasting operation routes its cotangent through _unbroadcast.

```python import numpy as np def _unbroadcast(g, shape): # undo the copies the forward pass pretended to make: summing is un-copying while g.ndim > len(shape): g = g.sum(axis=0) for i, s in enumerate(shape): if s == 1 and g.shape[i] != 1: g = g.sum(axis=i, keepdims=True) return g class Tensor: def __init__(self, data, parents=()): self.data = np.asarray(data, dtype=np.float64) self.grad = None self._parents = parents self._backward = lambda: None def _acc(self): if self.grad is None: self.grad = np.zeros_like(self.data) def __add__(self, other): other = other if isinstance(other, Tensor) else Tensor(other) out = Tensor(self.data + other.data, (self, other)) def b(): self._acc(); other._acc() self.grad += _unbroadcast(out.grad, self.data.shape) other.grad += _unbroadcast(out.grad, other.data.shape) out._backward = b; return out def __mul__(self, other): other = other if isinstance(other, Tensor) else Tensor(other) out = Tensor(self.data * other.data, (self, other)) def b(): self._acc(); other._acc() self.grad += _unbroadcast(out.grad * other.data, self.data.shape) other.grad += _unbroadcast(out.grad * self.data, other.data.shape) out._backward = b; return out def __matmul__(self, other): out = Tensor(self.data @ other.data, (self, other)) def b(): self._acc(); other._acc() self.grad += out.grad @ other.data.swapaxes(-1, -2) other.grad += self.data.swapaxes(-1, -2) @ out.grad out._backward = b; return out def relu(self): out = Tensor(np.maximum(self.data, 0.0), (self,)) def b(): self._acc(); self.grad += out.grad * (self.data > 0) out._backward = b; return out def log(self): out = Tensor(np.log(self.data), (self,)) def b(): self._acc(); self.grad += out.grad / self.data out._backward = b; return out def reshape(self, *shape): out = Tensor(self.data.reshape(*shape), (self,)) def b(): self._acc(); self.grad += out.grad.reshape(self.data.shape) out._backward = b; return out def sum(self, axis=None, keepdims=False): out = Tensor(self.data.sum(axis=axis, keepdims=keepdims), (self,)) def b(): self._acc() g = out.grad if keepdims or axis is None else np.expand_dims(out.grad, axis) self.grad += np.broadcast_to(g, self.data.shape) out._backward = b; return out def __getitem__(self, idx): out = Tensor(self.data[idx], (self,)) def b(): self._acc(); np.add.at(self.grad, idx, out.grad) out._backward = b; return out def backward(self): topo, seen = [], set() def build(v): if id(v) in seen: return seen.add(id(v)) for p in v._parents: build(p) topo.append(v) build(self) self.grad = np.ones_like(self.data) for v in reversed(topo): v._backward() ```

The fused loss is the one place where hand-writing the vjp is worth more than composing primitives:

```python def softmax_cross_entropy(logits, y): z = logits.data z = z - z.max(axis=1, keepdims=True) # exact by shift invariance, and it prevents overflow e = np.exp(z); p = e / e.sum(axis=1, keepdims=True) n = z.shape[0] loss = Tensor(-np.log(p[np.arange(n), y]).mean(), (logits,)) def b(): logits._acc() g = p.copy(); g[np.arange(n), y] -= 1.0 # dL/dz = (p - y)/n, derived above logits.grad += g / n loss._backward = b return loss ```

np.add.at in __getitem__ is the scatter-add that makes embeddings work: the same index may appear several times in a batch, and every occurrence must contribute.

Stage 3 — parameters and modules

```python class Parameter(Tensor): pass class Module: def __init__(self): self._modules, self._params = {}, {} def __setattr__(self, k, v): if isinstance(v, Module): self._modules[k] = v elif isinstance(v, Parameter): self._params[k] = v object.__setattr__(self, k, v) def parameters(self): out = list(self._params.values()) for m in self._modules.values(): out += m.parameters() return out def zero_grad(self): for p in self.parameters(): p.grad = None def __call__(self, *a): return self.forward(*a) class Linear(Module): def __init__(self, din, dout, rng, scale=1.0): super().__init__() self.W = Parameter(rng.standard_normal((din, dout)) * scale / np.sqrt(din)) self.b = Parameter(np.zeros(dout)) def forward(self, x): return x @ self.W + self.b class ReLU(Module): def forward(self, x): return x.relu() class Sequential(Module): def __init__(self, *layers): super().__init__() self.layers = list(layers) for i, l in enumerate(self.layers): self._modules[f"layer{i}"] = l # without this, parameters() sees nothing def forward(self, x): for l in self.layers: x = l(x) return x class Embedding(Module): def __init__(self, n, dim, rng): super().__init__() self.W = Parameter(rng.standard_normal((n, dim)) * 0.1) def forward(self, idx): return self.W[idx] ```

The comment on Sequential is the bug from the concepts section, fixed in one line. Every other line here is bookkeeping around object.__setattr__, which is the price of making attribute assignment register itself.

Stage 4 — optimizers

```python class SGD: def __init__(self, params, lr=0.1, momentum=0.0, weight_decay=0.0): self.params, self.lr, self.m, self.wd = params, lr, momentum, weight_decay self.buf = [np.zeros_like(p.data) for p in params] def step(self): for i, p in enumerate(self.params): if p.grad is None: continue g = p.grad + self.wd * p.data self.buf[i] = self.m * self.buf[i] + g p.data -= self.lr * self.buf[i] class AdamW: def __init__(self, params, lr=1e-3, betas=(0.9, 0.999), eps=1e-8, weight_decay=0.0): self.params, self.lr = params, lr self.b1, self.b2, self.eps, self.wd, self.t = betas[0], betas[1], eps, weight_decay, 0 self.m = [np.zeros_like(p.data) for p in params] self.v = [np.zeros_like(p.data) for p in params] def step(self): self.t += 1 for i, p in enumerate(self.params): if p.grad is None: continue self.m[i] = self.b1*self.m[i] + (1-self.b1)*p.grad self.v[i] = self.b2*self.v[i] + (1-self.b2)*p.grad*p.grad mh = self.m[i] / (1 - self.b1**self.t) # bias correction vh = self.v[i] / (1 - self.b2**self.t) p.data -= self.lr * (mh/(np.sqrt(vh)+self.eps) + self.wd*p.data) ```

Stage 5 — the training loop

```python def train(model, opt, loss_fn, batches, steps, log_every=250): for step in range(steps): xb, yb = next(batches) loss = loss_fn(model(xb), yb) model.zero_grad() loss.backward() gn = np.sqrt(sum(float((p.grad**2).sum()) for p in model.parameters() if p.grad is not None)) if gn > 1.0: # clip before stepping for p in model.parameters(): if p.grad is not None: p.grad *= 1.0 / gn opt.step() if step % log_every == 0: print(f"step {step:5d} loss {loss.data:.6f} |g| {gn:.3f}") return model ```

The gn printed on every log line is the global gradient norm; watching it per layer rather than in aggregate is how you find the depth at which a stack stops learning.

Stage 6a — XOR, end to end

```python rng = np.random.default_rng(0) X = np.array([[0.,0.],[0.,1.],[1.,0.],[1.,1.]]); Y = np.array([0,1,1,0]) net = Sequential(Linear(2, 8, rng), ReLU(), Linear(8, 2, rng)) opt = SGD(net.parameters(), lr=0.5, momentum=0.9) for step in range(3001): loss = softmax_cross_entropy(net(Tensor(X)), Y) net.zero_grad(); loss.backward(); opt.step() if step % 500 == 0: print(f"xor step {step:5d} loss {loss.data:.6f}") print("predictions", np.argmax(net(Tensor(X)).data, axis=1), "target", Y) ```

Output:

```text xor step 0 loss 0.633573 xor step 500 loss 0.000027 xor step 1000 loss 0.000016 xor step 1500 loss 0.000011 xor step 2000 loss 0.000008 xor step 2500 loss 0.000007 xor step 3000 loss 0.000006 predictions [0 1 1 0] target [0 1 1 0] ```

A network that could not be built from a single linear layer (M06) is now trained by code you wrote, and the loss falls by five orders of magnitude.

Stage 6b — a character-level language model

Context of $C=3$ characters, embedding width 8, one hidden layer of 32, vocabulary $V=28$.

```python text = "the quick brown fox jumps over the lazy dog. " * 40 chars = sorted(set(text)); V = len(chars) stoi = {c: i for i, c in enumerate(chars)}; itos = {i: c for i, c in enumerate(chars)} data = np.array([stoi[c] for c in text]) C = 3 Xs = np.stack([data[i:i+C] for i in range(len(data)-C)]) ys = np.array([data[i+C] for i in range(len(data)-C)]) print("vocab", V, "examples", len(Xs), "uniform loss", np.log(V)) # 28, 1797, 3.3322 emb = Embedding(V, 8, rng) W1 = Linear(C*8, 32, rng); W2 = Linear(32, V, rng) params = emb.parameters() + W1.parameters() + W2.parameters() opt = AdamW(params, lr=3e-3) for step in range(2001): idx = rng.integers(0, len(Xs), 64) xb, yb = Xs[idx], ys[idx] h = emb(xb).reshape(64, C*8) # (64,3,8) -> (64,24) loss = softmax_cross_entropy(W2(W1(h).relu()), yb) for p in params: p.grad = None loss.backward(); opt.step() if step % 250 == 0: print(f"lm step {step:5d} loss {loss.data:.4f}") ```

Output, with the uniform baseline $\log 28=3.3322$ for comparison:

```text lm step 0 loss 3.3078 lm step 250 loss 0.0169 lm step 500 loss 0.0124 lm step 750 loss 0.0125 lm step 1000 loss 0.0009 lm step 1250 loss 0.0226 lm step 1750 loss 0.0337 lm step 2000 loss 0.0219 ```

and sampling greedily from a temperature-scaled distribution:

```python def sample(seed_text, n=90, temp=0.2): out = seed_text for _ in range(n): ctx = np.array([[stoi[c] for c in out[-C:]]]) logits = W2(W1(emb(ctx).reshape(1, C*8)).relu()).data[0] / temp p = np.exp(logits - logits.max()); p /= p.sum() out += itos[int(np.random.choice(len(p), p=p))] return out print(sample("the q")) # one draw: 'the quick brown fox jumps over the quick brown fox jumps over the quick...' # the exact draw varies with the RNG state; temperature 0.2 keeps it close to greedy ```

The corpus is deterministic after three characters, so 0.0219 nats (0.032 bits per character) is what "solved" looks like for this task. Replace the corpus with real text and the same code becomes a (bad) language model — which is the point at which M12 and M14 take over.

Common misconceptions

"Autograd computes a symbolic derivative of your model."

It computes nothing symbolically. There is no expression tree that gets differentiated; there is a sequence of local vjps whose results are added into buffers. That is why the cost is a small multiple of the forward pass rather than a blow-up in expression size, and why you cannot ask autograd for "the derivative formula" without evaluating it at a point.

"The computational graph is built when you define the model."

Under define-by-run it is built by the forward pass, discarded after backward(), and rebuilt with a different shape if your batch size or control flow changes. This is why a if statement works, why retain_graph=True exists, and why a memory leak from keeping a reference to a loss tensor keeps its whole graph alive.

"Each layer type needs its own backward pass."

Each primitive needs one vjp — a dozen primitives cover essentially all of deep learning. A new architecture is a new arrangement of existing primitives, and only a genuinely new primitive (a new activation, a custom attention variant) requires new backward code. If you are writing per-architecture backward passes, you are working against the design.

"Broadcasting is just a convenience; gradients handle themselves."

The forward pass silently replicates data; the backward pass must sum the replicas, and a framework that forgets to reduce the gradient returns the wrong shape, which then broadcasts again into a plausible but wrong result. Every hand-written engine hits this bug exactly once, which is why _unbroadcast is the first function in the tensor implementation above.

"torch.compile makes the model mathematically faster."

It removes Python and dispatch overhead by tracing and fusing kernels, so the wall-clock speedup comes mostly from overhead and memory traffic, not from fewer FLOPs. The mathematics is the same graph, differentiated the same way; what changes is how it is executed, and — because fusion reorders floating-point operations — the last few digits of the results.

Exercises

Warm-up (check understanding)

  1. Write the __sub__ vjp for a tensor engine, including the sign.
  2. A tensor of shape $(3,4)$ is added to one of shape $(4,)$; what is the gradient's shape and its reduction axis?
  3. Count the parameters of $V=100$, $d=16$, $C=4$, hidden 64, vocabulary 100.
Solutions 1. `c = a - b` gives $\bar a = \bar c$ and $\bar b = -\bar c$, both routed through `_unbroadcast`. 2. $(4,)$, obtained by summing over axis 0 (the batch axis of size 3). 3. Embedding $100\times16=1{,}600$; hidden $(4\times16)\times64+64=4{,}160$; logits $64\times100+100=6{,}500$; total $12{,}260$.

Core (do the math)

  1. Derive the vjp of sum(axis=0) on a $(3,4)$ input, and say why the gradient of the output is broadcast_to.
  2. Add an exp primitive to the tensor class, build a LayerNorm module out of existing primitives, and finite-difference check its input gradient.
  3. Explain why Embedding needs np.add.at rather than self.grad[idx] += out.grad.
Solutions 4. The forward maps $X\in\mathbb{R}^{3\times4}$ to $y_j=\sum_{i=1}^3X_{ij}$. So $\partial y_j/\partial X_{ij}=1$ for every $i$, and $\bar X_{ij}=\bar y_j$: the output gradient is replicated along the summed axis, i.e. `np.broadcast_to(out.grad, X.shape)`. Summation is the inverse of replication, and vice versa — the same rule as broadcasting, in the other direction. 5. `exp`: forward `np.exp(data)`, vjp `self.grad += out.grad * out.data` (reuse the output, not a fresh exponential). `LayerNorm` as mean/variance/reshape primitives works but is slow; the point of the exercise is that it is *possible* without a new primitive, which is the claim that primitives compose. 6. `self.grad[idx] += out.grad` performs buffered fancy-index assignment, which only applies the *last* write for each duplicated index. `np.add.at` accumulates every occurrence, which is required because the same character can appear several times in a batch and each occurrence contributes a separate path from the embedding row to the loss.

Stretch (build or break it)

  1. Add a no_grad context manager (a module-level flag checked in Tensor.__init__ so that no parents are recorded) and measure the peak memory of an evaluation pass with and without it.
  2. Add a residual block x + f(x) to the language model, train to the same loss, and compare the gradient norm reaching the embedding layer with and without the residual.
Hints 7. Set a global `GRAD_ENABLED = True`; in `Tensor.__init__`, if it is false, store no parents and set `_backward` to a no-op. Under define-by-run, evaluation with gradients enabled builds a full graph that is never used, so peak memory grows from $O(\text{batch})$ to $O(\text{layers}\times\text{batch})$ — the same failure mode as a memory leak, and it appears as an out-of-memory during validation. 8. With a residual, the gradient at the embedding is dominated by the identity path and should be an order of magnitude larger and far less sensitive to depth; without it, the product of Jacobians through the hidden layers attenuates it (**M08**). Compare `np.linalg.norm(emb.W.grad)` in both runs at the same step count.

Self-test

  1. Name the four fields of a minimal autograd node and the role of each.
  2. Why does a broadcasting forward pass force a reduction in the backward pass?
  3. Give both vjps of $\mathbf{Z}=\mathbf{X}\mathbf{W}$ and check the shapes.
  4. Why is reverse topological order required, in one sentence and one edge case?
  5. What breaks if Sequential does not register its submodules?
  6. What does torch.compile change, and what does it leave alone?
Answers 1. `data` (the value), `grad` (the adjoint), `_parents` (the edges), `_backward` (the local vjp closure that pushes into the parents). 2. Because the forward pass conceptually made $n$ copies of the smaller operand, each contributing a separate path to the loss; the chain rule sums over paths, so the backward pass sums the copies back down. 3. $\bar{\mathbf{X}}=\bar{\mathbf{Z}}\mathbf{W}^\top$ of shape $(n,k)$ and $\bar{\mathbf{W}}=\mathbf{X}^\top\bar{\mathbf{Z}}$ of shape $(k,m)$, matching $\mathbf{X}$ and $\mathbf{W}$. 4. A node's adjoint needs the final adjoints of all its children; any order violating that adds an incomplete adjoint. Edge case: a node with fan-out, which is every parameter used twice. 5. `parameters()` returns an empty or partial list, the optimizer never sees those parameters, and the model trains only partially — loss still decreases, which hides the bug. 6. It changes execution: tracing, kernel fusion, and removal of Python/dispatch overhead. It does not change the graph's mathematics or the differentiation algorithm, though fusion can change the last digits of the numerics.
